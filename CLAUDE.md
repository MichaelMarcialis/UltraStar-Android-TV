# UltraStar Android TV — Project Brief

A minimal, purpose-built karaoke scoring app for a single specific Nvidia Shield TV Pro. Not a general-purpose product — scoped tightly to one household's exact hardware.

## The goal

A karaoke game that tracks and scores singers' pitch accuracy in real time (Karaoke Revolution / SingStar style), using either an existing library of community UltraStar-format songs or the user's own. Core loop: pick a song, scroll lyrics + a pitch bar in sync with audio/video playback, capture mic input, score against the reference melody.

## Why this project exists (context for decisions below)

The user tried UltraStar Play (the official Android TV port of UltraStar) on this exact Shield TV Pro first. It had four serious problems:

1. **Settings don't persist** — song folder path and other config reset on every app launch.
2. **UI not TV-friendly** — requires scrolling, elements land off-screen. Traced to a maintainer-acknowledged issue: a Unity dependency was stripped from the current Android build to fix a crash, which broke UI Toolkit styling/translations across the app.
3. **D-pad navigation barely works** — the UI is clearly touch-first. There's an opt-in "gamepad navigation" setting in Play, but it was itself flagged as buggy on some devices, not a reliable fix.
4. **Mic tracking fails in actual gameplay** — both wired mics test fine individually in Settings, but during a real song, one player's mic isn't captured at all. Originally attributed to a long-standing cross-platform UltraStar Play bug. **Since diagnosed as a Shield firmware problem, not Play's fault** — this device's USB audio HAL can't open these mics at all, so anything routed through Android's audio stack fails. See the mic section below; it's solved, but only by bypassing that stack entirely.

Researched mainstream "karaoke apps for smart TV" (Smule, StarMaker, Singa, Karaoke Anywhere) as alternatives — ruled out. They're subscription services built around licensed catalogs and vocal effects/social features, not open pitch-scoring against a user-provided library.

**Decision: build fresh rather than fork UltraStar Play.** Forking would inherit Play's actual bugs (the above), embedded in a large, unfamiliar Unity/C# codebase, on top of the user having zero prior Android development experience. A scoped-down native app avoids inheriting those specific bugs and can be dramatically smaller than Play's full feature set.

## Explicitly out of scope

- Song editor
- Cross-platform support (desktop/mobile) — Shield TV Pro only, single device
- Multi-language UI
- Anything from UltraStar Play's actual codebase — reuse ideas/formats, not code
- A phone/tablet companion mic app — was the planned fallback for two-player input, now unnecessary since two wired USB mics are working. The user's kids have no phones, so this was never desirable anyway.

## What to reuse from the UltraStar ecosystem (formats/ideas, not code)

- **Song format**: standard UltraStar `.txt` song folders (lyrics + pitch + timing data as plain text, paired with an audio file and a background video or image). Write an original parser for this format — it's simple, well-documented, and gives access to the entire existing community song library without touching Play's code.
- **Pitch detection**: the **YIN** algorithm (de Cheveigné & Kawahara, JASA 111(4), 2002) — the same method UltraStar and most karaoke scorers use. Implemented originally in `pitch/Yin.kt` from the published paper. TarsosDSP was the obvious library here and was used and verified first, but it's GPL-3.0 and isn't on Maven Central (only the author's personal repo), and this repo may be opened up publicly — so it was replaced with ~90 lines of original code. **Don't reintroduce a GPL audio library.** Note the algorithm itself is not the licensed part; only implementations are.
- **UI toolkit**: **Compose for TV** (`androidx.tv:tv-material`, `androidx.tv:tv-foundation`), not the older Leanback library. Leanback is now officially deprecated by Google in favor of Compose for TV. Note the historical naming gotcha: the Android manifest category for "show this app on the TV home screen" is still literally named `LEANBACK_LAUNCHER` for legacy reasons, even though it has nothing to do with the deprecated Leanback UI library — every TV app, Compose or not, still uses that exact category name.

## Mic input — SOLVED, but not the way you'd expect (read before touching audio)

**Do not use `AudioRecord` / `AudioManager` for mic input on this device. It cannot work.**

This Shield's USB audio HAL (`modules.usbaudio.audio_hal`) fails to profile *any* USB audio device, in *either* direction, with `adev_open_input_stream fail - cannot read profile` → `checkInputsForDevice: No input available`. It fires automatically on plug-in, before any app touches the device, so the mic never enters `AudioManager.getDevices()` and `AudioRecord` can never target it.

Ruled out exhaustively (2026-08-07 → 08-09): the USB hub, power, cabling, defective units, the user's debloat, firmware version (already latest), the stock remote being awake, capture-only vs duplex devices, SELinux, device-busy, the `usb_audio_automatic_routing_disabled` setting, and forcing a re-probe. Three mic products from three manufacturers all fail identically. USB audio *output* is broken too — confirmed by ear. The kernel is fine: `snd-usb-audio` binds and creates correct PCM nodes every time; the breakage is purely in Nvidia's userspace HAL, and it is unreachable without root.

**This almost certainly explains UltraStar Play's bug too** — Play's mics "tested fine in Settings" but failed during songs because gameplay capture went through this same broken HAL.

**The working architecture: bypass Android's audio stack entirely via the USB Host API.** Kotlin does permission → `openDevice()` → `claimInterface(force=true)` (which detaches the kernel's `snd-usb-audio`) → `setInterface(alt=1)`, then a small C layer pumps isochronous URBs over usbfs. No libusb, no root. Verified live: **two mics simultaneously at 93 KB/s each** (vs 93.75 theoretical) with independently responding levels.

**Two wired mics work — the phone-as-second-mic fallback is obsolete, drop it.** Implementation in `mic/`, harness in `diagnostics/IsoCaptureScreen.kt`.

Gotchas if you touch this code:
- The JNI symbol names in `cpp/usb_iso.c` encode the Kotlin package — moving `UsbIsoNative.kt` silently breaks it at runtime only.
- usbfs derives each iso packet's buffer offset by summing the *requested* lengths, so packet *p* sits at `p * maxPacketSize` when all packets request the max.
- usbfs signals URB completion as **POLLOUT**, not POLLIN.
- `struct usbdevfs_urb` ends in a flexible array member — size is `sizeof(urb) + packets * sizeof(iso_packet_desc)`.
- Android's `UsbInterface` does **not** expose class-specific descriptors; channel count / bit depth / sample rates only come from parsing `UsbDeviceConnection.rawDescriptors`.
- A USB mic reports `mHasAudioPlayback=true` even with no speaker — that's Android misreading the UAC "Output Terminal" (type `0x0101` = USB Streaming, i.e. audio *to* the host). It is not a duplex device.

**Mic audio format** (Let's Sing 2024, `046d:0a03`, parsed from raw descriptors): UAC 1.0, **mono, 16-bit signed little-endian**, supports 48000/44100/22050/11025/8000 Hz, endpoint `0x82` isochronous asynchronous, `wMaxPacketSize` 208, `bInterval` 1. Both mics share this VID:PID — tell them apart via `UsbDevice.getDeviceName()`, which is unique per port.

## Hardware and environment

- **Device**: Nvidia Shield TV Pro (2019 model). Confirmed via on-device Settings: Android version **11** (API level 30), security patch Jan 5 2026, build `RQ1A.210105.003`. ("SHIELD Android TV SW Version" 9.2.4 is Nvidia's own firmware layer on top of Android — a different number, not the OS version, don't confuse the two.)
- **minSdk 30 / targetSdk 37 / compileSdk 37**. minSdk matches the device exactly, so there's no backward-compatibility hedge to maintain — use any API 30-era API freely. (targetSdk 37 does mean newer-API behaviour changes still apply where the device supports them, e.g. `PendingIntent` mutability flags.)
- **Reboot with USB peripherals unplugged.** The Shield hangs on the Nvidia boot logo if the hub/mics/SD adapter are attached at power-on — reproduced three times, resolved every time by unplugging. Attach peripherals *after* it reaches the launcher. Almost certainly the bootloader's minimal USB stack choking on hub topology or inrush current.
- **Storage**: 1TB microSD card in a USB adapter, plugged into one of the Shield's two USB 3.0 ports, set up as Removable Storage. This is where the song library lives.
- **Microphones**: two wired USB mics (from Let's Sing 2024, PS5 version) — standard class-compliant USB audio devices, connected through a powered USB hub in the Shield's other USB port.
- **TV**: LG OLED. CEC handoff between the Shield and this TV has historically been unreliable — don't assume Shield-remote control of TV-level settings; the user may need the LG remote directly for anything TV-side.
- **Launcher**: Shield runs Projectivy (a third-party Android TV launcher replacing the stock home screen). Confirmed this doesn't affect anything architecturally — it reads the same standard `LEANBACK_LAUNCHER` manifest category every other TV launcher does, regardless of UI toolkit used internally.

## Dev environment

- Windows 11 PC, Git for Windows, Claude Code CLI run from Android Studio's terminal.
- Android Studio, SDK Platform 30 + Build-Tools, **NDK 30.0.15729638**, CMake (AGP auto-installs 3.22.1 to satisfy `cmake_minimum_required`).
- Project: **"UltraStar Android(TV)"**, package `com.example.ultrastarandroidtv`, Kotlin, Android TV template.
- Key Gradle config: Compose BOM `2026.06.00`, `androidx.tv:tv-material`, the **Compose Compiler Gradle plugin** (`org.jetbrains.kotlin.plugin.compose`, version-locked to Kotlin `2.2.10` — mandatory since Kotlin 2.0, and its absence causes a confusing compiler ICE rather than a clear error), `buildFeatures { compose = true }`, `externalNativeBuild` → `cpp/CMakeLists.txt`, `ndkVersion`, and `abiFilters = ["arm64-v8a"]` (the Shield is arm64-only, so don't build other ABIs).
- **Dependencies come from Maven Central and Google only** — no custom repositories, and every runtime dependency is permissively licensed. This is deliberate: the repo may be opened publicly, and a personal Maven host is a durability risk (it can vanish and break builds years later) as well as a licence question. Check both before adding anything.
- **There is more than one Shield on this network, and only one of them can run this app.** The dev device reports `ro.product.device` = **mdarcy** (2019 Pro) and `abilist64` = `arm64-v8a`. **Do not use `ro.build.product`** — the 2019 Pro reports `foster` for it too, which is the 2015 board name, so that check identifies the right machine as the wrong one (measured 2026-09-02). At least two **2015** Shields also answer adb here, and those are **32-bit**: `abilist` is `armeabi-v7a,armeabi` and `abilist64` is empty. The build ships `arm64-v8a` only, so installing on one fails with `INSTALL_FAILED_NO_MATCHING_ABIS` — which reads like a broken build and is nothing of the sort. **Check `ro.build.product` before installing.** The dev machine's own ARP table finds the candidates: NVIDIA's OUIs are `00:04:4B` and `48:B0:2D`, then `adb connect` each in turn.
- Deploys over network ADB (`adb connect <shield-ip>:5555`). The connection drops occasionally mid-install with `InstallException: EOF` — just `adb disconnect` + `adb connect` and retry, it's not a code problem. If the device shows as `unauthorized`, the Shield is waiting on its "Allow USB debugging" prompt.
- **`export MSYS_NO_PATHCONV=1` before any adb command with a device path.** Git Bash rewrites `/sdcard/foo` into `C:/Program Files/Git/sdcard/foo`, and `adb push` then fails with a baffling `remote secure_mkdirs failed`. Costs an hour if you don't know it.
- **The whole TV UI can be driven from here**, which is how the song library and the document picker were tested without asking anyone to pick up a remote:
  - `adb exec-out screencap -p > shot.png` then read the image — the fastest way to see what is actually on the TV.
  - `adb shell uiautomator dump /sdcard/ui.xml` gives the view tree with `focused="true"` and `bounds`. Use it rather than guessing: several TV widgets show no visible focus ring, so a screenshot alone will convince you focus is lost when it isn't.
  - **`input tap` coordinates are in 1920x1080, but `screencap` returns 3840x2160.** Halve screenshot coordinates or taps land off-screen and silently do nothing. Take bounds from the uiautomator dump instead, which is already in input space.
  - The Shield sleeps on its own; `adb shell input keyevent KEYCODE_WAKEUP` before a test run. A sleeping display stalls anything driven by frame callbacks.
  - **Relaunch with `am start -S`, not `am force-stop` then `am start`.** Force-stopping while the activity is mid-transition (notably with the IME open) can leave the task record stuck: the new process starts, the mics open, and then no window is ever focused — a black screen and an ANR reading *"does not have a focused window"*, with the app at 0% CPU. Looks exactly like a startup hang in your own code and is not one. `-S` stops it cleanly first and the same build launches fine.
- Build/test from the CLI needs `JAVA_HOME` set to Android Studio's bundled JBR: `export JAVA_HOME="C:/Program Files/Android/Android Studio/jbr"`.

## Current state

**Done:**
- **Song parser** (`song/`) — full UltraStar `.txt` parsing: headers, note types (normal/golden/freestyle/rap/golden-rap), line breaks, duets (`P1`/`P2`), comma-decimal values, BOM handling, plus beat↔time conversion. Covered by JVM unit tests (`./gradlew testDebugUnitTest`). Known gap: `#RELATIVE:YES` beat offsets are not implemented (rare, deliberately deferred).
- **USB mic capture** (`mic/` + `cpp/usb_iso.c`) — see the mic section above. Two mics simultaneously, confirmed on hardware.
- **Pitch detection** (`pitch/`) — `Yin.kt` is an original YIN implementation (no third-party DSP dependency; see the reuse section above). `PitchTracker` runs it, one instance per mic, fed straight from `UsbIsoCapture`'s callback: it buffers the ragged USB chunks into 2048-sample windows sliding by 1024 (~47 readings/s, 43 ms latency, allocation-free in steady state). Three gates before a reading counts as voiced — window RMS, YIN confidence, and a 65–1200 Hz range that bounds the lags searched rather than filtering after. Plus `Pitches.kt` (Hz↔MIDI, note names, cents). Unit tests cover pure tones, sawtooth/square waves and a missing fundamental (the cases where octave errors actually happen — pure sines prove nothing there), noise, and silence. **Verified on hardware** with a 4-octave reference sweep (A2/A3/A4/A5 read back exactly, no octave errors), both mics live at 45–47 readings/s each, 100% voiced on sustained notes, 0% on silence.

- **Scoring** (`score/`) — `PlayerScorer` consumes timestamped `PitchReading`s against one `VoicePart` and produces a `ScoreSnapshot` (note points / golden bonus / line bonus, adding to 10000, plus hit counts). Pure JVM logic, no Android. Covered by 26 unit tests including an end-to-end pass over real parsed song text; three deliberate mutations were each caught by the test written for them.
  - **Scores per beat, not per reading** — each beat is judged by sampling the singer once at its midpoint. This is the load-bearing decision: it keeps the maximum a property of the song alone, so a dropped USB packet or a change to the analysis hop size can't change what a perfect performance is worth.
  - The beat takes whichever of the two readings *bracketing* its midpoint is nearer. Taking simply the first reading after the midpoint means a one-beat note can be scored from audio belonging to the note after it.
  - A beat whose nearest reading is more than `maxHoldSeconds` (default 100 ms) away scores as unsung rather than reusing stale audio — otherwise a capture stall would score beats nobody sang.
  - Pitch offset resolved: **UltraStar pitch 0 = C4 = MIDI 60**. Sanity check: songs use roughly −20..20, which maps to E2..G#5. Scoring can't get this wrong regardless, since it compares `mod 12` and 60 is a multiple of 12 — the offset only affects display and note height.
  - `NoteScore` keeps the sung fractional MIDI **per beat** (NaN = nothing sung), which is what a pitch bar draws as the singer's trace, and what distinguishes "sang nothing" from "sang the wrong note".

- **Playback engine** (`playback/`) — Media3/ExoPlayer 1.11.0 (Apache-2.0, Google's Maven). `SongPlayer` wraps the player; its real job is `SongClock`.
  - `SongClock` exists because `ExoPlayer.getCurrentPosition()` is callable only from the player's own thread and updates in coarse steps, while ~47 readings/s arrive on capture threads that must not touch the player. The owner re-anchors it once per frame; everyone else extrapolates with `System.nanoTime()` off a single volatile immutable time base, lock-free.
  - **It never runs backwards while playing.** Small backwards corrections are treated as jitter and ignored, since the scorer's cursor can't rewind. On backwards jitter the time base is left *untouched* rather than rewritten with the value it already yields — re-anchoring recomputes the same instant from a new origin and can land a bit lower in the last place, which a reader sees as the song stepping back. `lastCorrectionSeconds` publishes the jitter so it stays a measurement, not an assumption.
  - **Sync is one number for scoring and two for drawing** (`SyncCalibration`). Output and capture+analysis latency sit on the same path, so a *reading* describes `playerPosition(now) − total` (`songTimeFor`). Anything *on screen* uses the output share alone, since that is how far behind the player the singer's ears are — **plus `displayLeadSeconds`, which is added rather than subtracted** because it describes a frame that has not been seen yet (`heardSongTimeFor`). The two audio delays are always *subtracted*: they describe the past, and flipping the sign doubles the error instead of removing it.
  - `LatencyProbe` measures that number by listening for tones at known song positions; median, so one masked tone can't move it.

- **Song library** (`library/`) — the user picks a folder once with `ACTION_OPEN_DOCUMENT_TREE`; `LibraryLocation` takes a **persistable** grant and re-checks it against `persistedUriPermissions` on every launch, so a stale stored URI becomes "pick the folder again" rather than a permission error deep in a read. **This is the fix for problem #1** — the setting Play lost on every launch.
  - No required folder, and songs must *not* live under `Android/` (which the scan skips, along with `LOST.DIR`, `System Volume Information` and dot-folders). The card's `UltraStar/` folder is what is granted today.
  - `SafDocumentTree` queries the content resolver directly rather than using `DocumentFile`, which asks the provider a fresh question per attribute per file. One query per folder instead of dozens of cross-process round trips.
  - `SongLibraryScanner` is written against a narrow `DocumentTree` interface, so all the scanning rules are unit-tested against an in-memory fake instead of needing a device and a granted folder. Each `.txt` is its own song (duet variants sit beside originals); media headers are matched by file name only, case-insensitively, because the paths inside them describe someone else's machine; a broken song is collected into `failures` and the walk carries on.
  - `SongTextDecoder`: BOM if present, else strict UTF-8, else Windows-1252 (**not** ISO-8859-1 — they differ exactly at `0x80`–`0x9F`, which is where the curly quotes and dashes in real song titles live).

- **Gameplay UI** (`game/`) — the game itself, verified on hardware in both layouts. `GameSession` owns the player, the mics and a `PlayerScorer` per singer; `NoteTrack` draws; `GameTheme` holds every colour and dimension in one file so the look can be tuned without reading drawing code.
  - **The layout follows the song, and it is one component either way.** A solo song is one track with a trace per singer (directly comparable — you see who is closer); a duet is a track each. Tracks are built from the song's *voice parts*, not from the mics, so a duet still shows both lines when only one mic is plugged in. Welding the lyrics to the scrolling notes is what made a track self-contained enough for one component to serve both.
  - **Karaoke Revolution-style scrolling marquee**, chosen by the user over the per-line static board UltraStar and SingStar use. Notes flow right-to-left past a fixed playhead at 30% width — most of the screen is lookahead, because the note *coming* matters more than the one just sung. Syllables scroll welded to their own notes, so **a rest is a real gap on screen** and the rhythm is read as spacing rather than inferred.
  - **The pitch scale is completely static — no zoom, no pan.** It covers the song's whole range and never moves. Three versions got here: scaling to the whole song squashed every phrase into a third of the height; resizing per passage fixed that and made the notes visibly stretch and squash; fixing the span and panning the centre fixed *that* and still drifted enough to distract. The user's call, and the right one — **any motion in the reference frame costs more than the resolution it buys**, because a singer is trying to read the notes, not admire them. A `PitchRange` class existed for the middle two answers and was deleted; the history is in git if it is ever wanted back.
  - The trade is real and accepted: a wide song ("Free" spans 22 semitones) puts each phrase in a narrow band with dead space above and below. That is the price of a frame of reference that never moves, and it buys the shallow track below.
  - **The track is a strip along the bottom (~26% of the screen, ~22% each for a duet), scores along the top.** The whole middle is deliberately empty — it is where the song video goes. A static scale is what makes a strip viable: nothing has to leave room for the view moving.
  - **Strict time-proportional lyrics are unreadable on real songs** (`LyricLayout`). At 5 s across the screen, fast syllables get roughly a quarter of the room their text needs — the TV showed "Butsomething" and "Byougivemehe". Syllables may now be pushed **later, never earlier**, and never more than `maxLagSeconds` from their own note. Offsets are precomputed for the whole song in absolute coordinates: a per-frame layout would depend on which syllable was first visible and the text would jitter as notes scrolled in.
  - **Do not restart the syllable chain at each lyric line.** It looks tidier and reads worse — it lets a new line land on the pushed tail of the last one, which is the most visible collision there is, right where a new phrase starts. The per-syllable cap already bounds drift, so the reset bought nothing. Both the fix and the trap are pinned by tests.
  - **A note is drawn exactly as tall as the window that scores it**, so "the arrow is inside the bar" and "this beat counts" are the same statement rather than two things that happen to correlate. This is why `pitchClassDistance` is now fractional: rounding the sung pitch to the nearest semitone first silently widened every tolerance by half a semitone each way, which is how a singer could sit visibly off the bar and still be credited. `ScoringConfig.toleranceSemitones` is therefore **also a visual constant** — change it and the bars change height.
  - `NoteScore` now keeps **per-beat hit flags**, so the note lights up exactly the beats that were paid for. Re-deriving that at draw time would put the tolerance rule in two places, and the day they disagreed the bar would quietly start lying about the score next to it.
  - **A Karaoke Revolution pitch arrow, not a line plot** (`ArrowMotion`, `drawArrows`). The first version plotted every beat already sung; the user asked for KR's arrow instead, and it is the better instrument. The singer's history is already told by the notes lighting up behind the sing line, so the plot restated it in a second visual language while cluttering the notes they were reading ahead in. One arrow per singer sits just left of the line, points at it, and says the one thing the notes cannot — *where your voice is right now*. Pitch becomes a vertical gap: level means right.
  - The arrow's pitch is **folded into the drawn octave** first. Scoring compares pitch classes, so an octave-displaced hit scores — pinning the arrow to the floor of the track while the score climbed would read as a bug. It folds against the note under the line, or the nearest visible one during a rest, so it keeps its bearings between phrases.
  - Arrow smoothing is **two-stage, and only ever on the display path**. A median of the last 3 readings (`GameSession.Singer.observe`) removes the lone wild readings that make the arrow twitch, then `ArrowMotion` eases the rest. It was 5 until the chain was measured end to end — see the input-latency section. Raw YIN on a real voice is honest rather than tidy, and drawn literally it looks like the detector is unsure when it is not. **The scorer is still fed the raw reading**, so the filter cannot quietly change what a performance is worth. Silence hides the arrow rather than freezing it — "not singing" must not look like "singing the same note" — but the position is *remembered* through short gaps, so a breath mid-phrase does not cause a snap.
  - **Sparks fire where the arrow meets the bar**, struck procedurally from the clock rather than simulated: no particle state, no per-frame allocation, nothing to leave behind when a note ends. They are gated on **the same comparison the scorer makes**, so they cannot disagree with the points.
  - **The shower is deliberately large** — 34 particles over 120 dp. The first version (16 over 46 dp) was legible but read as a rendering artefact rather than as a reward, which is the opposite of what the game's one moment of praise should do. Each spark varies independently in **speed, trail length and fan angle**, drawn from the same hash with different salts: one number driving all three correlates them, and a shower where every particle follows the same path at the same rate reads as a rotating pattern rather than as sparks. Colour runs white → gold → orange in three stops, because a straight white-to-orange ramp spends its whole middle in washed-out cream.
  - The arrow is deliberately **narrow (17 dp)**: in two-player mode both arrows share the sing line and spend much of a song within a few semitones of each other, so a tall arrow means constant overlap.
  - **The arrow is one solid shape.** It had a translucent halo behind it to stay findable against a busy note field; at a glance that reads as two arrows of different weights rather than as one emphasised arrow, and the sparks now do the standing-out.
  - **The song announces itself on a title card, and the corners belong to the scores.** The title and artist used to hold the top-left corner for the whole song — read once, then occupying a corner for three minutes — while both scores shared the other. Now the name is shown large in the centre for 2.2 s before the music starts, fades over 0.9 s as playback begins, and the singers take a corner each: the same left/right split as their colours, their arrows and, in a duet, their tracks. The card also covers the ~1 s load stall, which is exactly the moment everyone is waiting anyway.
  - **The game gets out of the way during long instrumentals** (`VocalBreaks`). Intros, solos and outros run half a minute, and an empty pitch track sitting over the video for all of it says "something is wrong" when the answer is "nothing is happening yet". A gap of 10 s or more with nobody singing fades the *whole* HUD out, and it comes back three seconds before the next note. Measured **across every part in play**, not per singer — in a duet one voice resting while the other sings is not a break in the song. The thresholds are asymmetric on purpose: leaving is unhurried (1.5 s hold, so a held note can finish), returning is early (the notes must have scrolled in and the eye must have found the sing line before anyone is asked to sing). A song's intro counts as a break like any other, so the title card fades straight into the bare video. Pure and unit-tested; the minimum gap is what stops a medium gap dipping halfway and coming straight back.
  - Both fades — the title card and the instrumental break — are read **inside a `graphicsLayer` block**, so neither costs a recomposition. The track is never removed from the tree while hidden: taking it out and putting it back would re-measure every syllable in the song, which is the expensive thing that makes startup stutter.
  - Threading: each scorer has exactly one writer (its own mic's capture thread) so **the audio path takes no lock**. The draw pass reads live `NoteScore`s while they are written; those are single 32-bit fields, so a frame can be one write behind but can never see half a value. Score readouts are only republished when the number actually changes — writing them every frame is what made the diagnostic screens expensive.
  - **The visible window is 2.25 s, tuned on the TV rather than chosen on paper.** Five seconds felt like sensible lookahead and crowded the lyrics badly — the narrower the window, the more pixels each second of song gets. It is a Settings dial now; the live D-pad tuning that found the number is gone, and gameplay handles only pause and back.
  - **There is a third latency, and it runs the other way** (`SyncCalibration.displayLeadSeconds`). Output and capture latency both describe *sound* that has already happened, so both are subtracted. The delay between drawing a frame and the TV showing it describes *light that has not been seen yet*, so it is **added**. Missing it showed up exactly as reported from the sofa: the lyric is sung a moment before it reaches the line. **Dialled in at 40 ms** — raised live on the D-pad until the lyric met the line as it was sung. Judged by eye and ear rather than measured by the app, so less precise than the 127 ms, but a real observation on the real TV. Re-check it if the TV or its picture mode changes.
  - **`SongPlayer.volume` exists but nothing exposes it.** It was on the D-pad briefly and was removed: a control that turns the *whole* song down is not what anyone means when they ask to turn the singer down, and offering it invites the misunderstanding.
  - **There is no way to turn down just the original vocal.** Checked: all 8 songs on the card are a single mixed MP3, with no `#VOCALS:`/`#INSTRUMENTAL:` headers and no second audio file. Vocals cannot be isolated from a finished stereo mix without either (a) centre-channel cancellation, which is a cheap trick that also guts bass and drums and collapses to mono, or (b) proper stem separation done offline on the PC (e.g. Demucs), writing `#VOCALS:`/`#INSTRUMENTAL:` files the app could then mix between. (b) is the real answer if this is wanted; it is a library-preparation workflow, not an app feature.
  - **A syllable's trailing space is data.** It is the only thing in the UltraStar format that marks the end of a word — `"some"` + `"thing "` is one word, `"but "` + `"you"` is two — and the parser was trimming whole lines, which threw it away. Nothing noticed until hyphens were added and every syllable came out hyphenated: `"I- was- suf- fo-"`. Note lines now keep their trailing spaces (`trimEnd('\r', '\n')`, not `trim()`), pinned by a parser test that builds its fixture by concatenation so a formatter cannot silently strip the space back out.
  - **Hyphens and tildes** (`syllableTexts`). A word split across notes gets a trailing hyphen — "fu-" "ture's" — which is how every karaoke game shows it and the difference between reading a word and reading two. `~` is an UltraStar convention from the song files marking a held syllable; it is stripped, and a syllable that was *only* a tilde draws nothing. No hyphen is ever left pointing at something invisible.

- **Claiming a microphone** (`ui/ClaimScreen.kt`, `game/MicClaim.kt`) — the fix for "am I player 1?".
  - The complaint was never really about attribution. **No label on a screen can say which of two identical microphones is in your hand**, so the microphone answers it instead.
  - **One singer is set up at a time, from beginning to end**: sing, take a microphone, choose a name, and only then does the next colour open. Three versions got here. The first asked the room for both singers at once and was **a race** — tested with the user's children (2026-08-18), both start yelling the moment a meter appears. The second named the microphone instead ("who has microphone 1?"), which does remove the race, and still failed in the same room for a different reason.
  - **The meter belongs to the singer, not to the microphone, and it stays up while they choose a name** (2026-08-19, the user's call). That is what the naming version was missing: it decided correctly and then *took the evidence away*, because the meters disappeared the instant a claim landed — which is exactly when two children who both shouted need to know which of them the app heard. Now one card sits on the right for the colour being set up and does not move, resize or vanish when the question changes from "sing" to "who are you", so a claim that went to the wrong child is **recoverable by singing**: one of them sings, and the meter says whether the name about to be chosen is theirs. The screen is a row rather than a column for exactly this — so the card can stay put across the transition instead of being redrawn somewhere else.
  - It also costs nothing vertically, which matters when the software keyboard is up and covering the bottom of the screen. The meter carries a tick at the gate, so "loud enough" is a target rather than a guess.
  - **When more than one mic hears a voice the screen says so** (`MicClaim.contested`). A claim that will not land because two children are singing is otherwise indistinguishable from broken hardware — on this device, a believable conclusion.
  - **The microphone is always discovered, never named** — one rule, no modes. A `namesTheMicrophone(micCount, playerCount)` helper used to switch between the two on a count and it is gone; git has it. Naming assumed the mic the app picked was the mic the singer picked up, which stops being true the moment a third audio device is attached, and that is not hypothetical: `findAudioCaptureTargets` matches any USB audio device with an isochronous IN endpoint, so a webcam counts. Singing into the one in your hand proves it works *and* says which one it is, in the same breath — and with a spare on the table it is the only question that has an answer at all.
  - Before a claim the meter shows **whichever free mic is loudest**, because which one was picked up is precisely the open question; after it, only that singer's own, so the next singer's voice cannot move it.
  - Three conditions to claim, all earning their place: loud enough (**the same threshold gameplay scores with**), clearly louder than every other mic (they hear each other across a room, so absolute loudness alone would let one voice take both slots), and held for a third of a second (a cough should not commit anyone). Pure and frame-driven, so it is unit-tested without a device.
  - **The margin was measured only against the mics still free, which meant the last slot had no margin at all.** With two mics and the first one claimed, the runner-up was always zero, so `bestLevel >= runnerUp * dominance` was trivially true and the second slot went to whatever the second mic could hear — usually the first singer, across the room, into a microphone they were not holding. It is now measured against *all* mics, claimed or not. Pinned by a test named for the failure; the old behaviour had a test asserting it, which is how it survived.
  - **Names are asked every game and never remembered against a microphone.** In a house with four children the mic is the one thing that does *not* identify a person — it gets handed to whoever sings next. Remembering would confidently put last night's name on tonight's singer, which is worse than asking. The list is ordered **most recently used first**, which is the only memory that actually predicts anything.
  - **The keyboard's dictation button cannot hear these microphones, so it is now asked not to appear** (2026-08-19). It is Gboard's button and it hands off to `KatnissRecognitionService` — Google's TV voice service, a separate process that opens its own input through Android's audio stack. That stack is the one this device's USB HAL cannot serve, so the singing mics are not merely deprioritised there, they are invisible. Nothing can be injected either: `SpeechRecognizer` takes no audio source, and the button belongs to the keyboard rather than to this app. Making it work would mean replacing the system keyboard *and* bundling an offline recogniser fed from the USB PCM — the same rejection as below, for the same reasons, and a name is a once-per-person cost the profile list then remembers.
  - **An offer the app cannot honour is worse than no offer**: pressing it and holding a microphone up teaches the room that the microphone is broken, which on this device is a conclusion already too easy to reach. `NameEntry` therefore sets `privateImeOptions` to `noMicrophoneKey` (plus the `nm` compat spelling and the package-qualified form, since the field is comma-splittable and the check has changed shape over the years), through Compose's `PlatformImeOptions`. **Gboard honours it** — confirmed by screenshot on the device, mic icon present before and gone after, with typing unaffected. It is a request rather than a guarantee; a keyboard that ignored it would simply show the button again.
  - **Rejected: coloured tape on the mics.** It works in one household and breaks the moment anyone else uses the app. Also rejected, for now: recognising a spoken name. Android's `SpeechRecognizer` cannot hear these mics at all — it captures through the broken `AudioRecord` path — so it would mean an offline engine and a model on disk, and it is weakest exactly where it is needed (new names, children's voices). Both mis-hearings and duplicate names would still need a remote-driven fallback, so it adds to the work rather than replacing it.
  - **`UsbMicSession` now lives for the life of the app** (created in `AppRoot`) with a settable `onAudio`, because the mics have to be open before gameplay for any of this. Reopening them per screen would repeat the permission dance and race the capture threads.
  - **The mic list is live, and it had to become live before the menu could refuse anything.** `UsbMicSession.mics` is a snapshot list refreshed on `ACTION_USB_DEVICE_ATTACHED`/`DETACHED`, so plugging a microphone in enables Play where it stands. Without that, "plug in another microphone" would be advice the app then ignores — worse than never offering the button's reason at all. **The refresh is deliberately additive**: a mic that is still attached is left completely alone, capture thread and all, because rebuilding the list wholesale would tear down and reopen working captures every time anything was plugged into the Shield, and reopening is the one operation on this hardware with a history of not coming back. `OpenMic.index` is therefore a `var` — unplugging the first of two has to renumber the survivor, or a screen indexing a per-mic array by it reads the other singer's voice.

- **Menus, settings and song browsing** (`ui/`) — `AppRoot` is a `when` over five screens, deliberately not a navigation library: this is a five-screen app that has to still build in five years.
  - **Player count is asked before the song**, because the answer changes what a song *is*: one singer collapses duets to a single line and scores one microphone, since splitting the screen would show a part nobody is covering.
  - **A choice the hardware cannot honour is refused where it is offered, with the reason.** No microphone disables Play on the main menu; one microphone disables "Two". The alternative is walking somebody through counting singers, claiming a mic and choosing a song before the problem surfaces — or worse, accepting "two" and then quietly scoring one person, which looks exactly like the second microphone having failed. **Focus follows what can actually be pressed**: a disabled TV button cannot take focus, so requesting it there leaves the screen with no focus at all and no way to move, which on a remote is a dead end.
  - **Settings persist** (`settings/GameSettings`) — display lead, visible window, mic sensitivity. Same reason the song folder does: this app exists because Play forgot its settings every launch. Written through to disk on every change, because there is no natural "save" moment on a TV.
  - The dials **look like sliders and are driven with left/right**. A drag slider on a television is hostile — there is no pointer, and emulating one with a directional pad is worse than not having the control.
  - **The gate and the word for it run in opposite directions.** What the audio code needs is a threshold — how loud a sound must be before it counts — and raising that makes the microphone hear *less*. Exposing it directly under the label "sensitivity" had the slider contradicting the plain meaning of the word. `GameSettings.micSensitivity` converts between the two (1 = hears the most), tested as exact inverses, so no screen has to remember which way round it goes.
  - **Mic sensitivity is the only lever against crosstalk.** With two singers in a room and a TV playing the song, each mic hears the other singer and the speakers, and all of it scores. Loudness is the only proxy for proximity these microphones give, so the gate is raised (`PitchTracker.minLevel`, default now 0.06 against the old 0.01). Blunt — sing quietly enough and it ignores you too — which is exactly why it is a slider and not a constant.
  - **Two singers see a "Duet" or "Versus" badge on every cover.** The format does distinguish them: a duet marks its lines `P1`/`P2`, which the parser turns into separate voice parts. Gold for a duet because it is the rarer and more interesting answer; the ordinary case is stated plainly so "no badge" never has to mean "not checked yet". **Only shown with two singers** — on your own a duet collapses to a single line anyway, so the distinction has nothing to say. The badge chip is nearly opaque, unlike the panels over the video: it sits on artwork chosen by somebody else and as likely to be near-white as near-black.
  - **Every screen in the setup flow has its two exits as visible buttons**, not just as the remote's back button. On the song list they are "Change singers" (back to the microphones and names, which is the thing most likely to be wrong by then) and "Main menu"; the claim screen has the same pair. The claim screen needs them most — it waits on a voice, so without them there is nothing on it to press, in exactly the case that strands you.
  - **Only finishing a song earns the library its place back.** Returning to the songs *from a song* lands back where it was; every other route in opens at the top. Both the main menu and **"Change singers"** clear it — a new lineup is a new start in the only sense that matters, because the song that suited the last singer is not evidence about the next one, and landing halfway down the row on somebody else's choice is the same disorientation as landing at the top after finishing. Two lambdas in `AppRoot` (`toMenu`, `toClaim`) clear it, which is why every button bound to those destinations goes through them rather than setting the screen itself.
  - **The library opens on the song that was just sung**, not at the top. Coming back to the start of a fifty-song row after finishing something is disorientating, and the one card anyone has their bearings from is the one they just chose — the next song is usually near it. The song is identified by its `.txt` document id, which is unique per song, and `ChosenSong` already outlives the game screen so nothing extra had to be remembered. Falls back to the first card when the song is not there, which is not theoretical: a Rescan between one song and the next can remove it, and a row that opened on nothing would have no focus at all and could not be driven by a remote.
  - **A `LazyRow` does not compose what is off screen**, so this is a scroll *then* a focus, and the focus requester the target card carries does not exist until it has been composed. Asking straight after `scrollToItem` is too early; the effect waits for frames until the request lands.
  - **The song picker is a horizontal row of album covers, and focusing one previews it.** Covers are decoded off the card with `inSampleSize` (no image library — one format, one place, one size). The preview is debounced by 450 ms so scrolling the row stays silent and stopping on a song plays it. Browsing by ear matters most for exactly the people this is for, who may not read quickly yet.
  - **The claim flow is confirmed with real voices** (user, 2026-08-17): singing into a microphone claims it and leads into selecting or creating a profile, at the shipped threshold, in the real room. So the default `micSensitivity` is not obviously wrong, which was the open question.
  - **Gameplay is confirmed with real voices, over whole songs** (user and children, 2026-08-17). Note bars fill with the singer's colour when sung at the right pitch, with the arrow touching the bar. That closes the last unproven link in the chain: microphone → pitch → beat → score → what is drawn. Everything from the USB bypass to the hit-fill is now verified by somebody singing rather than by a synthetic signal.
  - **Whether the scoring is too harsh is open, and it is a judgement rather than a bug.** The calibration harness settles the mechanical half: feeding the song back to itself scores 9766–9922 of 10000, so a performance that is genuinely on pitch and in time is not being penalised by anything systematic. What is unsettled is how much slack a *person* should get, which is one number — `ScoringConfig.toleranceSemitones`, default 1.0.
  - **Changing that number changes the picture as well as the score.** A note is drawn exactly as tall as the window that scores it, so widening the tolerance makes every bar visibly taller and "the arrow is inside the bar" stays a true statement rather than becoming a rough guide. That is the property to preserve if a difficulty setting is ever added: it must move the drawing and the scoring together, which it does automatically as long as both keep reading the same constant.
  - **A name already claimed this game is not offered to the second singer at all.** One person cannot be holding both microphones, so picking the first singer's name is never what was meant, and allowing it puts the same word in both top corners for a whole song. Removed from the list rather than shown and refused — an option that cannot be chosen is only there to be pressed by mistake. Typing it reaches the same collision by another road, so that is refused too, with the reason on screen: a Done button that silently does nothing is worse than allowing it. Matching ignores case and surrounding space, the same way `Profiles.use` folds "mia" onto an existing "Mia"; the two have to agree or a name in the wrong case walks straight past the rule. The comparison lives in `settings/Profiles.kt` as free functions rather than methods, because `Profiles` needs a `Context` and the rule does not — which is what lets it be tested.
  - **`ui/ProfilesScreen.kt` is the full list**: add, rename, remove, reached from a top-level "Singers" item on the main menu. **Not inside Settings**, and that was a deliberate call — Settings is about the machine (latency, microphone sensitivity, how far ahead the notes scroll), set once by whoever put this together, while the list of people changes whenever a friend comes round. Burying it would also hide it at the only moment it earns its place, which is somebody setting up before anyone has sung. Adding puts the name at the **front** (whoever bothers to type a name in is usually typing the name of the person about to sing); renaming **keeps its position**, because a correction is not a use and fixing a typo should not reorder who is likely to sing next. Removal asks first, and **"Keep" takes the focus, not "Remove"** — on a remote the confirmation and the press that caused it are the same button, so a default of "yes" is no safer than no confirmation at all.
  - **Typing pushes everything else off the screen, on purpose.** The on-screen keyboard covers the bottom of the TV, and it covered the Add and Cancel buttons until the screen's title and subtitle were dropped while a field is open. Anything left above a text field costs a button below it. `ui/NameEntry.kt` is the single field both screens use, shared because taking focus at the right moment is the one thing that makes the keyboard appear at all, and two copies would eventually differ in exactly that.
  - **One singer goes through the claim step too**, and always has. It is not ceremony: with two microphones plugged in, the dominance rule is what identifies *which* one the person picked up, and the name is what ties the game to a profile — which is the hook for anything later (avatars, leaderboards). Verified on hardware: one slot, one claim, then straight to the songs.

- **Managing the library from the TV** (`ui/SongsScreen.kt`) — a top-level "Songs" item on the main menu: where the songs are, what is wrong with them, and removing one. Everything here used to need a PC and a card reader.
  - **It is the only screen that shows a song which cannot be sung.** The picker hides them on purpose — a card that does nothing when pressed is worse than no card — but hiding them *everywhere* is how a library quietly fills with rubbish nobody can see or clear out.
  - **`#MP3:` is now optional, and that is the load-bearing change.** The parser used `required("MP3")`, so all 22 audio-less folders threw `SongParseException` and never became songs at all — they landed in `failures`, which nothing rendered. `ScannedSong.isPlayable` could therefore never actually be false: the state it describes was unreachable. A chart with no audio named is **incomplete, not invalid**, and the difference is whether the app can talk about it. Pinned by tests in both the parser and the scanner.
  - **The folder grant needed widening, and only the picker can widen it.** `LibraryLocation` took read alone, because playing never needs more. Deleting does, and `takePersistableUriPermission` can only confirm what the picker just handed over — there is no later prompt that upgrades a live grant in place. So `remember()` now takes read **and** write, and `canModify()` exists so a folder chosen by an older build says "choose the folder again to remove songs" instead of showing a Remove button that fails.
  - A folder to itself is deleted whole — chart, audio, video, artwork. A folder holding **two arrangements** loses only the one text file, and the confirmation says which of the two is about to happen. "Keep" takes the focus, the same rule as removing a singer.
  - The cache now holds **every** song and the picker filters at draw time (`SongLibraryCache.playable`). Filtering before storing meant the broken ones were thrown away at the one moment they had already been paid for.

**Downloading songs in-app** (researched 2026-08-18, **re-measured and started 2026-08-20**). The user asked for USDB-Syncer-style search and download inside the game. It was parked in August because the media half needed four moving parts. **That is no longer true, and the whole reason it changed is one yt-dlp release.**

- **The August conclusion, kept because the reasoning still applies elsewhere**: USDB serves charts only, so audio comes from YouTube, and yt-dlp 2026.07.04 hit `HTTP 403` needing a JS runtime, a PO-token provider built from source, *and* an authenticated session. Three of those four parts are JavaScript. The card was the evidence: every audio-less folder had the chart and the cover and **no audio** — the half that would move into the app had never failed, and the half that breaks was the hard half.
- **What changed**: yt-dlp **2026.8.19** picks the **`visionos`** client, whose yt-dlp entry declares `REQUIRE_JS_PLAYER: False`. Measured against this library: **no cookies, no PO token, no JS runtime, no Python**. Every other client still fails (403, or a PO token demanded, or no formats).
- **So it is three plain HTTP calls**, verified by hand and then on the Shield: `GET youtube.com` for a `visitorData` session token → `POST /youtubei/v1/player` with a client context → `GET` the URL that comes back. Implemented in `net/YouTubeAudio.kt` with **no new runtime dependency**.
- **Chaquopy is not usable here anyway.** 16.1.0 calls `org.gradle.util.VersionNumber`, removed in Gradle 9, and this project is on Gradle 9.5.0. Do not spend time on it — nothing needs it now.
- **The known hole is "made for kids"**, which the visionOS client cannot see. Of 19 audio-less charts on the card, **13 fetch and 6 do not**, all Disney/Trolls. They are *alive* — the `android` client reads their titles — but their streams demand a PO token. The fix is searching for a different upload, which is what the Add-songs screen is for. **Do not record those ids as dead**: the oembed check on 2026-08-18 called them alive and it was right; it just does not predict whether a stream can be fetched.
- **`#MP3:` is written to match whatever was saved.** Streams arrive as `audio/mp4` (AAC, itag 140) by preference over higher-bitrate Opus-in-WebM, because the Shield decodes AAC in hardware and Opus in software, and a song already costs 52–55% of a core with video. Pinned by a test, since "take the highest bitrate" looks like an obvious cleanup.
- **A video's duration is not the song's.** Thriller resolves to 13:42 — the long-form horror video — so a chart matched to the 6-minute song will not fit it. `ResolvedAudio.durationSeconds` exists so a screen can say so before downloading.

**USDB itself** (`usdb/`, mapped against the live site 2026-08-20 — every fact here is measured, not inferred from USDB Syncer's source):

- **Everything needs an account.** Anonymous requests for the song list answer *"You are not logged in."* Only the RSS feed of the ten newest songs and bare page titles are public. Sign-in is an ordinary form post (`user`, `pass`, `remember`) and the session is a `PHPSESSID` cookie **lasting 6 days**.
- **Never hard-code credentials, and never ship an account.** The app asks each person for their own USDB login and offers a sign out — the user's explicit instruction, and the only thing that works if this is ever opened up. A development account's details belong in a file outside the repo, never in source, a test, or a command line.
- **USDB throttles chart downloads on purpose, and the app honours it.** Asking for a chart returns a countdown page — **24 seconds**, reduced for people who upload songs — and only then does `POST wd=1` hand over the file. **Do not work around this.** It is their bandwidth, and users are signed in as themselves, so an app that hammered USDB would get *their* accounts blocked for something they cannot see. The screen must say so plainly: a song takes about half a minute, ten take five minutes, and an honest countdown beats a spinner that looks stuck.
- **The search form is rich**: artist, title, edition, language, genre, year, creator, golden-notes, sort field and direction, page size and offset. `details=1` is always sent — it adds a **cover thumbnail** (`data/cover/{id}.jpg`, 200x200) and, unexpectedly, **a thirty-second iTunes audio preview per row**. That is the "preview before you download" requirement solved without YouTube and without an account beyond USDB's.
- **Columns are located by their header `id`** (`list_artist`, `list_title`, …), never by counting: `details=1` inserts two columns at the *front*, so any fixed position is wrong in one of the two modes. Rows are found by the `data-songid` they carry.
- **No HTML library.** The markup is old and partly unclosed, which is normally the argument *for* a parser — but the `<td>` elements are well formed and targeted extraction was demonstrated against real pages before the code was written. `test/resources/usdb/search_results.html` is a **genuine captured page**, trimmed to three songs and with the account name replaced; sanitise any fixture before committing it.
- **A chart's `#VIDEO:` header carries USDB Syncer's meta tags** — `v=` video, `a=` audio when it differs, `co=` cover, `bg=` background, `medley=`. Take audio from `a=` when present or the sound belongs to the wrong upload.

- `adb push` writes files *and* whole folders straight into `/storage/5002-E7C7/UltraStar` with the card in the Shield (tested). **The card never needs to come out.**

**Assembling a song** (`download/SongDownloader.kt`, built 2026-08-20):

- **Nothing is written until the audio is in hand.** This is the rule the class is arranged around, and the card is why: 19 folders hold a chart, a cover, sometimes a video and **no audio**, because the desktop tool created the folder and *then* failed to fetch the sound. Order is chart → video id → resolve → **download the audio** → only then create a folder. If the writing itself fails part way the folder is deleted, so a failure leaves nothing rather than a convincing ruin. Verified on hardware: a refused video left the card at 68 folders, unchanged.
- **The provider names the files, not us.** SAF may rename what it creates — a clash gets a suffix, some providers correct an extension to match the MIME type. So media is written *first*, its real names are read back from the tree, and the chart's headers are pointed at those. A chart written first would be guessing, and a `#MP3:` off by one character is a song that silently will not play.
- **`#MP3:` is rewritten and `#COVER:` inserted; `#VIDEO:` is left alone.** USDB charts name an mp3 that has never existed, and this app saves `.m4a`. `#VIDEO:` keeps its meta tags because they record where the media came from. **Only header lines are touched and line endings are preserved byte for byte** — note lines carry meaning in their trailing spaces, which is how every syllable got hyphenated the one time a whole file was trimmed.
- **A cover is a nicety, audio is not.** Artwork that fails to download does not fail the song, and no `#COVER:` is written pointing at a file that is not there.
- **A song already on the card is refused before any request is made.** Two folders for one song is worse than not downloading — both appear in the picker, identically.
- **Filenames follow the card's own convention**: `Artist - Title/` holding `Artist - Title.txt`, `Artist - Title.m4a`, `Artist - Title [CO].jpg`. A slash becomes a hyphen rather than vanishing (the card stores "Huntr/x" as "Huntr-x", not "Huntrx").
- **Proved end to end on the Shield**: signed in, searched, found two versions of "a-ha - Take On Me", tried the MTV Unplugged one and got `AUDIO_UNAVAILABLE` leaving nothing behind, tried the original, waited USDB's 24 s, downloaded 3.86 MB of AAC and the cover, wrote the folder. The app's own scanner then read the library as **50 playable, 0 failures**, up from 49, with the new song `playable=true`. 172 s for two attempts, of which 48 s was USDB's throttle.
- **The availability check is built** (`usdb/UsdbDetails.kt`, 2026-08-21). The detail page names the same YouTube id the chart will, with no wait, so a doomed song is refused in about two seconds instead of twenty-seven. Verified on the TV against Kelly Clarkson's "Since U Been Gone". The chart still has the last word: its id is compared with the pre-checked one and the lookup is only skipped when they agree. Safe because `a=` and `v=` are alternatives, never both present — measured across all 68 sidecars on the card, and confirmed against four live detail pages, three of them `a=`-only.

**The "Add songs" screen** (`ui/AddSongsScreen.kt`, `download/DownloadQueue.kt`, built 2026-08-20) — a top-level button on the Songs screen, beside Change folder and Rescan. Sign in, search, hear a sample, queue a download. Driven end to end from `adb` on the real TV.

- **Downloads are queued, one at a time, and the queue now lives in `AppRoot` rather than on this screen** (2026-08-23; see below). A song costs about half a minute of USDB's throttle, so watching each one finish before choosing the next would make picking five songs a five-minute stare. Never more than one at a time — parallel downloads would defeat the wait rather than respect it, and it is the *user's* account that gets blocked.
- **The wait counts down out loud** ("USDB asks us to wait — 18s"). A spinner there reads as a hang; a number going down is visibly not stuck, and it names who is waiting so the app does not look broken.
- **Every result carries a thirty-second iTunes sample and a cover**, both free with `details=1`. Focusing a row previews it after 450 ms, the same debounce the song picker uses. That matters most for the people this is for, who recognise a song long before they recognise its title.

**Two bugs found only by driving the real screen, both worth keeping:**

- **A stream must be fetched with a `Range` header or it crawls.** Measured against one URL: a plain `GET` came back at **31 KB/s**, the identical request with `Range: bytes=0-` at **10.1 MB/s** — a 324× difference. Google throttles whole-file requests to roughly playback speed, which is sensible for a video player and ruinous for a download. Without it a four-megabyte song takes about two minutes and looks exactly like a hang; the first on-screen test sat on "Downloading the music…" for 90 seconds and *did* eventually succeed, which is the worst kind of failure. It lives on `AudioFormat.fetchHeaders` and is pinned by tests in two files, because it reads like a no-op that a tidy-up would delete.
- **Focus must be requested on a row that can actually take it.** A song already on the card is shown but disabled, and a disabled TV button cannot receive focus — so "focus the first result" silently did nothing whenever the first hit was one you already owned, which is what happens every time somebody looks for more by a band they like. The screen was left with focus nowhere and no way to move, the same dead end the main menu avoids with a greyed-out Play. Focus now goes to the first row that is not already yours, and to nothing at all when none are, leaving the cursor in the search field where the next useful action is.

Also learned on the TV: **`input tap` does not work on Compose TV buttons** — they are focus-driven, so drive them with `KEYCODE_DPAD_*` and `KEYCODE_DPAD_CENTER`. And **a `LazyColumn` has not composed its first row when results arrive**, so focus has to be re-requested over successive frames, exactly as the song picker documents for its `LazyRow`.

**What "already yours" is read from is live state, not the library cache.** A successful download *clears* that cache so the Songs screen rescans — which meant every "Already yours" marker vanished the moment anything downloaded. The screen now keeps its own set and adds to it as songs land.

**The keyboard covers the bottom two-thirds of the television and roughly the right half with it.** The sign-in form's first draft cleared it by about four pixels, which is not clearing it; everything is now kept high and tight, and the error line sits *below* the buttons so an error cannot push them under the keyboard at the moment they matter most. The search row originally held five controls and "Sign out" wrapped into a vertical stack of letters while "Back" fell off the right edge entirely — the exact fault that made UltraStar Play unusable. Ways out now live in the top-right corner, which was empty anyway.

**The USDB login lives in private storage** (`usdb/UsdbAccount.kt`). The password is kept, not just the cookie, because the session lasts six days and the alternative is typing a password with a remote every week. It is in the app's private prefs — not encrypted, and worth being straight about why: anyone with `adb` on this Shield can read it via `run-as`, and Keystore would not stop that either since `run-as` runs *as this app*. The protection that does matter is applied — the file is **excluded from backup** in both `backup_rules.xml` and `data_extraction_rules.xml`, so it never leaves the device. **Never bundle an account**: each user signs in as themselves, which is also what stops one person's throttle breach becoming everybody's.



**Music videos, better covers, and one search box** (2026-08-21, all four from an evening's testing on the real TV):

- **A downloaded song now brings its music video.** It is the same YouTube video the sound came from, so it costs no extra lookup, and `#VIDEO:` is **not** rewritten — the scanner already falls back to any video file in the folder, which is how every video in this library is found. The video is fetched **last, after the song is complete**, precisely so a failed video cannot discard a good song; a song without one still gets the visualiser.
  - **It is streamed to the card, not held in memory.** `dalvik.vm.heapgrowthlimit` on this Shield is **192 MB** and a 1080p video runs to 60–100 MB, so buffering one next to Compose and a decoder is an out-of-memory kill waiting to happen. `Http.openStream` and `DocumentWriter.writeStream` exist for this one caller; both have defaults that buffer, so every test fake and every other implementation was untouched.
  - **A smaller video does not download any faster, so quality is free.** Every rung took ~100 s, which read at the time as YouTube serving at playback rate. **Re-measured 2026-08-23 and the cause was different**: every one of those formats was over the 10 MiB per-response limit, so all four were throttled equally. Fetching in bounded chunks removed it entirely — see the chunking section below. The conclusion holds for decoder reasons rather than bandwidth ones. One song, four formats (2026-08-21): 1080p h264 58 MB at 0.58 MB/s, 720p h264 22 MB at 0.22 MB/s, 1080p VP9 33 MB at 0.33 MB/s, 480p h264 14 MB at 0.14 MB/s — **100 seconds each, within a second of one another.** Dropping quality costs picture and saves nothing but card space, of which there is a terabyte. So `pickVideo` takes the best h264 up to 1080p.
  - **Never AV1**, which is the rule that cannot be got wrong: the Tegra X1+ has no AV1 decoder, and AV1 is the *smallest* file at every rung — exactly what a well-meant "take the smallest" would pick. h264 first because every video already on the card is h264; VP9 is the fallback and would halve the size if space ever mattered.
  - **The video stage counts a percentage** for the same reason USDB's wait counts down out loud: it runs for about a hundred seconds, and a hundred seconds of "Downloading the video…" reads as a hang.

- **Covers are 1000x1000 instead of 200x200.** USDB serves exactly one cover per song and it is genuinely 200x200 — visibly soft on a 4K set and softer than the rest of the library, whose covers the desktop tool fetched full-size. Three sources are now tried in order, lazily, and a cover failing still never fails a song:
  1. **The chart's own `co=` tag when it is a full URL** — the author's choice, often 1400px. Only ~11 of 68 charts on the card qualify.
  2. **iTunes** (`net/ITunesArtwork.kt`) for the rest. Not a new trust boundary: USDB has already matched every song to an iTunes track, which is where the thirty-second preview on each search row comes from. Artwork size is a path segment, so `100x100bb.jpg` becomes `1000x1000bb.jpg` by string surgery.
  3. USDB's thumbnail, still there as the last resort.
  - **fanart.tv is unreachable and that is why iTunes is needed at all.** 57 of the 68 `co=` tags are a bare fanart filename rather than a URL. The path shape is right (`images.fanart.tv/fanart/{name}.jpg`) but Cloudflare answers any plain client `403 cf-mitigated: challenge` — verified from two different TLS stacks, so it is not a matter of sending better headers.
  - **A wrong cover is worse than a soft one**, so a result is taken only when the title matches by containment *and* the artist shares a word. Requiring *every* word was tried against all 77 folders and lost seven — every soundtrack, because "Disney's Moana (Dwayne Johnson)" is billed by iTunes as "Dwayne Johnson".
  - **USDB's own `[DUET]` tag has to come out of the query first**, found on the real screen rather than in a test. Asking Apple for "ABBA Gimme! Gimme! Gimme! (A Man After Midnight) [DUET]" returns Olivia Newton-John and a punk covers band with ABBA nowhere in the results; without the tag it is the first hit. Square brackets are stripped, **round brackets are not** — "(A Man After Midnight)" is the song.

- **One search box instead of Artist and Title.** Nobody looking for a song thinks in fields, and on a remote each field costs a trip through the on-screen keyboard. USDB's form has no field spanning both — checked against the live form, which offers `interpret` and `title` and nothing else — so one keyword becomes **two searches**, merged with artist matches first and repeats dropped. Both halves earn their place: measured on the live site, `interpret=gone` finds one song on the whole of USDB and `title=gone` finds fifty-nine. Searching is the part of USDB that is *not* throttled, so the second request is cheap.

**The "super tall button" bug, and why it looked like that** (reported from the sofa with a video, 2026-08-21):

A failed download stretched one row of the results list to the full height of the screen, in the shape of a dome, with the reason unreadable inside it. The cause is a Compose layout rule rather than anything about downloads: in a `Row`, a child with no weight is measured **before** the weighted one beside it. The status text at the end of the row had no width limit, so a long failure message took the entire row and left the title `Column` nothing — and the title then wrapped to **one character per line**. The dome was simply `RoundedCornerShape(50%)` applied to something far taller than it was wide.

- The fix is two-part and both halves matter: the trailing slot is capped (`widthIn(max = 250.dp)`, one line, ellipsis) and says only a few words — `shortStatusLabel`, which exists solely so a sentence can never go there — while the **reason moves to the second line** in place of the song's details, where it has the row's width and a two-line cap.
- `HttpFailure` was making it worse: `orThrow` put **400 characters of the server's raw HTML** into the message. That is now stripped of tags and capped at 120 characters (`summarise`).
- **Diagnosed from the user's phone recording with `ffmpeg`**, the same method as the flashing bug: sample frames to a filmstrip, find the anomaly, read the text off a full-resolution frame.

**Why that song would not download, and the one class of song that still cannot** (measured 2026-08-21, correcting an earlier note):

- "Since U Been Gone" is **region-blocked**, not missing: YouTube answers `UNPLAYABLE` with "The uploader has not made this video available in your country" — the *same status* as a deleted video. `RefusalKind.REGION_BLOCKED` now separates them, read from the reason text, because the advice differs: waiting never helps, another upload usually works. The reason may only ever *narrow* the answer, never widen it, since it is localised prose that will drift.
- **The made-for-kids failures are not what the earlier note said.** It claimed those streams "demand a PO token"; the measured picture is more specific. The `visionos` client — the one that needs no JS runtime, no cookies and no token — **cannot see those videos at all** (`UNPLAYABLE`). The `IOS` and `ANDROID` clients *can*, and hand out working URLs, but only when the stream is fetched with that client's own User-Agent, and then only in ranges up to about **256 KB**: 64/128/256 KB succeed, 512 KB and above are `403`. That cap applies to the iOS client for **every** video, not just kids ones — a normal video is refused whole-file on iOS too — so it is an un-attested-client limit rather than anything about the song.
- **So the remedy is a different upload, not a different client**, which is what the Add songs screen and the availability pre-check are for. Splitting a download into sub-256 KB chunks would work and is deliberately not built: it defeats an anti-bulk-download control, and users are signed in to USDB as themselves.

**Library management, rebuilt** (2026-08-23/24). Seven things the user asked for in one pass; every one of them is on the real TV and the real card.

- **The download throttle was never what we thought, and the fix is 71×** (`net/RangedDownload.kt`). `Range: bytes=0-` was believed to be the whole answer because it took a 3 MB *song* from 31 KB/s to 10.1 MB/s. Re-measured against a 77 MB video, one request carrying that header is throttled exactly as hard as one carrying none: **what YouTube meters is how many bytes a single response carries.** Measured, one request per size, each from a different offset so nothing came from the last test's cache:

  | asked for in one request | rate |
  |---|---|
  | 8 MB | 49.9 MB/s |
  | 10 MB | 66.3 MB/s |
  | 12 MB | **0.72 MB/s** |
  | 16 MB | **0.72 MB/s** |

  The knee is exactly 10 MiB. A whole-file fetch runs at a flat 0.72 MB/s **from its first megabyte** — not a burst then a clamp — and an explicit end (`bytes=0-20971519`) does not help. So all media is fetched in **5 MiB chunks**, half the limit. 40 MB took 55.4 s as one request and 0.8 s as chunks. **On the Shield: a 58.5 MB video plus 4.6 MB of audio, start to finish, in under five seconds** — that video alone was ~100 s before.
  - This is *not* the sub-256 KB chunking that was deliberately not built for made-for-kids videos. That one slips under a cap on an un-attested client, which is an attestation bypass. This is ordinary ranged HTTP against a stream we are entitled to fetch, and is how every video player on the internet works.
  - `AudioFormat.fetchHeaders` no longer carries a `Range` — the chunker owns it. A format setting its own would quietly put the wrong one back.
  - **The earlier "a smaller video does not download any faster" measurement is now explained**: every quality took ~100 s because every one of them was over 10 MiB. The conclusion drawn from it (take the best h264 up to 1080p, never AV1) still stands, for the decoder reasons rather than the bandwidth ones.

- **Downloading outlives the screen that starts it** (`download/Downloads.kt`, created in `AppRoot` beside `UsbMicSession`). The worker used to be a `LaunchedEffect` inside `AddSongsScreen`, so pressing Back cancelled the download and lost USDB's throttle wait with it — which made queueing pointless, since the whole value of a queue is being able to go and do something else. The USDB session moved with it, so walking away no longer signs you out either.
  - **Held for the whole of a song.** Gameplay costs 52–55% of a core with video, and a download is network plus a burst of writes to the same card the song is streaming from. The hold is taken at **stage boundaries, never mid-transfer** — parking inside a video's per-buffer progress callback would leave an HTTP connection open across a three-minute song and time it out. One in flight finishes its current step, which is now seconds rather than a hundred of them.
  - A finished download announces itself wherever you are (`ui/DownloadNotice.kt`): one line, bottom right, gone after six seconds, **takes no focus** and is not drawn during a song.

- **One progress bar instead of a run of countdowns.** `QueuedSong.progress` is monotonic and computed by a pure `stageProgress`; `queueProgress` averages the queue. The weights are seconds and USDB's throttle is now ~75% of a download, which is the honest shape of the thing. **Monotonic matters:** "getting the song" is reported twice, before the countdown and again to collect the file, so reading the stage straight off sent the bar back to 4% having sat at 80%. A row says a percentage; the sentence naming the step — USDB's countdown included — is said once above the list.

- **Repair** (`download/SongRepairer.kt`, `download/RepairQueue.kt`) — filling in what a song on the card is missing, without downloading it again.
  - **It costs no USDB account and no throttle.** Everything needed is already in the folder, so a repair is a lookup and a download — three or four seconds against twenty-seven.
  - **The load-bearing discovery: those charts have no `#VIDEO:` header at all.** USDB Syncer moves the meta tags *out* of the chart and into a `.usdb` file beside it, and **all 19 audio-less folders on this card have one** carrying `a=`/`v=`. So the video id is read from the chart first (which is where *our* downloads keep it) and from the sidecar otherwise. `usdb/UsdbSidecar.kt` reads it leniently and never writes one — filling in another program's format with fields we do not track would have that program act on them.
  - `ScannedSong.sidecarId` is recorded during the scan, because the folder listing is already in hand there.
  - **Only offered when there is an answer.** A Repair that says "there is nothing I can do" is worse than no Repair. The button also names what it will fetch — "Get the music", "Get the video" — because getting a song's music back and fetching a nicer picture are not the same act.
  - **"Repair N songs" counts only songs missing their *music*.** Sweeping in everything incomplete would catch the twenty-five with no video and mean downloading twenty-five music videos nobody asked for.
  - **`DocumentWriter.overwrite` had to exist.** SAF resolves a name clash by *suffixing*, so writing a chart back under its own name leaves the old one and adds `Artist - Title (1).txt` — which the scanner reads as a second song and the picker offers twice. `retargetChart`'s `audioFile` is now nullable so a cover-only repair cannot destroy the header naming the music.
  - `SongLibraryCache.markStale()` replaces `clear()` for "the card changed": the next visit rescans, but what is already known stays readable. Clearing outright made every "Already yours" marker vanish the instant anything downloaded.
  - A finished batch rescans **once**, when the queue goes idle — per song it would cost more than the repairs.
  - **The USDB song id is now written into every chart we download** as `#USDBID:`. Nothing reads it yet; it is written because it can only be known at the one moment the app holds both the chart and the id, and working it out later means guessing from artist and title. That is the groundwork for an update feature, which is deliberately not built.

- **A failed download tries another version of the same song** (`download/AlternateVersions.kt`). Only on `AUDIO_UNAVAILABLE` — a folder that will not write or no internet are facts about this machine that another chart would hit identically.
  - **Searches USDB, not YouTube.** Matching an arbitrary YouTube result to a chart is where the Thriller problem lives: that song resolves to a 13:42 video and a chart timed to the six-minute single will not fit it. USDB usually holds several charts per popular song, each against a different upload — another *matched pair*, not a guess. Searching is unthrottled and the detail page names its video for free, so checking six candidates costs about a dozen seconds and no wait.
  - **Artists are matched with spaces stripped and on containment**, not on a shared word. A shared word was tried first and matched "The Monkees" to "The Beatles" on the strength of "the". Containment survives "a-ha"/"aha" and "Disney's Moana"/"Moana" and cannot make that mistake.

- **The Add songs screen is a rail and a grid, and it draws its own keyboard** (`ui/KeyGrid.kt`). A third for asking, two thirds for answers, after the Plex layout the user supplied.
  - **The keyboard is the point.** Every keyboard injury this app has taken is one problem — Gboard covers the bottom two-thirds of a 1080-line screen: the sign-in form clearing it by four pixels, the profile screen dropping its own title, five controls not fitting across a search row, three spellings of `noMicrophoneKey` to hide a button that cannot hear these mics. Drawing the keys removes the class of them.
  - **Searching runs on its own**, 800 ms after typing stops, because a Search button on a letter grid is another journey across the screen. Affordable precisely here: USDB's search is the unthrottled part.
  - **Nothing takes focus away from the keyboard.** The old list focused the first result to dismiss the IME; with keys on the page that reason is gone and doing it anyway is actively wrong — results now arrive *while somebody is still typing*. Measured on the TV: typing "abba" produced "abl", because the search for "ab" returned between the second letter and the third and the grid took the cursor out from under the next press. Right moves into the results, and focus search skips a card that cannot be pressed, so the "first hit is already yours" case needs no handling at all.

- **The Songs screen is a grid of covers** with sort and filter chips across the top and an A–Z rail on the right (`library/SongBrowsing.kt` holds the rules, pure and tested). Five columns; the filters are Ready / No music / No video / No artwork, all states the scanner already knows. **"Has updates" is deliberately absent** — nothing can tell yet whether a chart changed on USDB, and a filter that always matches nothing is worse than none. A filter matching nothing is disabled, because on a remote an empty screen with the focus in it is a dead end. Only the letters something files under are offered, `#` first.

The user's call was that it should: a song with no video and a song wearing a 200-pixel thumbnail are both worse than they need to be, and the machinery was already written. On this card that took the count from 6 to 23.

**Eight things a review caught** (Copilot on PR #2, 2026-08-24). All eight were real; two changed a rule rather than a guard.

- **A title that merely *contains* another is a different song.** `AlternateVersions` matched titles by containment so that `[DUET]` would not break a match — but "Hello" is contained in "Hello Again", so a song whose music had gone could be replaced by a **different song**, which is the one failure nobody notices until they press play. Titles are now compared for equality after USDB's square-bracket arrangement tag is stripped. **Square brackets only**: a round bracket is usually part of the song, or marks a genuinely different recording — "(Hardstyle)" — and folding those together is the same mistake by another road.
- **Artwork does not come from YouTube, so it must not need a video id.** `plan()` returned null whenever the folder did not say where its media came from, which refused a *cover* repair that iTunes could have done from the artist and title alone. `RepairPlan.videoId` is nullable now, media needs are computed separately from artwork needs, and YouTube is only asked when there is media to fetch — so a removed video no longer blocks fetching a better picture.
- **An empty 2xx mid-download was treated as the end of the file**, which wrote a truncated song and reported success. With a declared length unmet that is a short read and now fails, the same way a declared-length 416 already did.
- **`fetchInChunks` used a remote `contentLength` as an allocation size**, bypassing the 64 MiB cap `UrlHttp` applies to whole-body reads. A length over 2 GB truncates to a negative int and throws before a byte is fetched. Capped and bounded, and the cap is enforced as bytes arrive rather than trusted up front.
- **`overwrite` truncated a chart before knowing the new bytes would land.** `"wt"` empties the file first, so a card that fills or is pulled out mid-write left nothing where the chart used to be — and the chart is the one part of a song that cannot be fetched again. The old bytes are read first and written back on failure. Not a temp-and-rename: a failure *between* the delete and the rename loses the chart just as completely, with more to go wrong.
- **A failed chart rewrite left its media behind.** SAF suffixes a name that is already taken, so each retry added another orphan while the song still would not play. The new file is deleted with the failure.
- **A replacement that could not delete the original announced success anyway**, leaving both songs in the library with one of them silent. The delete is checked and the wording says what is actually there.
- **The download notice expired while it was hidden**, so a download landing in the first seconds of a song was erased six seconds later and never seen. The timer starts when the notice is visible. Late news is still news; no news looks like a download that vanished.

**A second review pass, and one of the findings was a fix that did not work** (Copilot on PR #2, 2026-08-25). Four more, all real.

- **The artist was being sent to USDB *and* judged locally, so the loose matcher never saw the charts it was written for.** `AlternateVersions` searched `interpret=Disney's Moana (Auli'i Cravalho)`, which the server cannot match against the Alessia Cara credit — the exact real-library case the bracket-stripping rule had just been added for, filtered out before `sameSongAs` ran. **Every test passed and the feature still could not work**, because the tests pinned the matching and nothing pinned the request. It searches by arrangement-free **title alone** now, and `AlternateSearchTest` pins the form that goes out.

Partial success is still success: one asset of three is worth having.
- **A video-only repair could delete a playable song.** Its failure carries `AUDIO_UNAVAILABLE` too, so the replacement path fired for a song whose only fault was a missing music video. Guarded on `plan.needsAudio`.
- **`overwrite` truncated even when it had no backup to restore.** Reading the old bytes is not a nicety there, it is the whole safety of the method — so a failed read now refuses the write outright. The caller reports a failed repair and cleans up its own orphan, which is strictly better than a destroyed chart.

**A third review pass, and the one it found by asking for tests** (Copilot on PR #2, 2026-08-25).

- **A bar that opened nearly full.** Both queues keep finished entries on purpose — a row saying "Added" or "Try again" is the most useful thing on the Add-songs screen, and a song's own page shows what its last repair did — but *progress* was averaged over all of them. Repair one song after a batch of twenty-three and the bar opened at 96%, twenty-three of the twenty-four jobs being already complete. Each entry now records which **run** it belongs to (a run ends when nothing is left in flight), and progress, the fixed count and the summary all describe the run in front of you. Copilot did not name this one; it asked for the tests that found it.

Unknown is treated as shared now, so the worst a bad listing can do is leave a chart behind.
- **`RepairQueue` and the scanner's sidecar discovery had no tests**, though both are load-bearing: the sidecar is what makes every desktop-created broken song repairable, and its failure is silent — no Repair button, and nothing anywhere saying why. Twenty tests added, including a *directory* named `something.usdb`, which is not a sidecar and would fail at the moment somebody pressed Repair.

**A partial repair used to be its own dead end** (2026-08-25). Getting the music but not the artwork is reported as a success — one asset of three is worth having — and it leaves a plan behind. But `RepairQueue` only let a **failed** job be asked for again, and `holds()` counted a finished one as still held, so the song's own button was hidden and "Repair N songs" skipped it. The rest of that plan could not be attempted again for the whole session, while every rescan went on saying there was something to fetch. **A fourth review pass, and both findings came from earlier fixes** (Copilot on PR #2, 2026-08-26).

- **A repair plan is only true for the scan it was worked out from.** Letting a *finished* job be re-queued fixed the partial-repair dead end and opened a worse hole: the Songs screen keeps its plans until the batch ends and rescans, so pressing Repair mid-batch ran a plan that still said `needsAudio` for a song that now had audio — fetching the music again, being handed a **suffixed copy** by SAF, and repointing the chart at it. `SongLibraryCache.generation` counts readings of the card, `RepairPlan.scan` records which one a plan came from, and `RepairQueue.blocks` reads it: a **failed** job is never in the way, an **unfinished** one always is, and a **done** one is until somebody has looked at the card again.
- **Artists are compared for equality, never containment.** "Queen" sits inside "Queens of the Stone Age", so with a shared title the old rule could have downloaded the other act's chart *and deleted the original folder*. The measured cases never needed containment — "a-ha"/"aha" and "Guns N' Roses"/"Guns N Roses" match on letters alone, and the two Moana billings match once the bracketed credit is stripped. The cost is a real miss, recorded in a test: a soundtrack billed plain "Moana" is not matched against "Disney's Moana". That is the right way round, because a missed alternative is a song somebody searches for by hand and a wrong one is a song that quietly disappears.

**A fifth review pass, and the tests it asked for found a real one** (Copilot on PR #2, 2026-08-26).

- **The request was bounded; the reply was not.** `openStream` accepts any 2xx, so a server, proxy or redirect that ignores `Range` answers **200 with the whole file** — appended to bytes already collected that writes the beginning twice, and with no declared length every pass appends the whole body again and **the loop never ends**. `HttpStream` now carries the status and `Content-Range`, and a whole body is accepted only as the *first* piece (which is simply the whole file) and then finishes. A 206 whose `Content-Range` starts somewhere else is refused outright.
- **One sidecar, or none.** A folder can hold two arrangements, and USDB Syncer writes a sidecar per download — so two charts can sit beside two sidecars naming *different* videos. Handing whichever was listed first to both would let a repair fetch one arrangement's music and point the other's chart at it, which is the Magic Dance failure. Refusing to guess costs repairability for such a folder, which is strictly better than repairing it wrongly. (A sidecar does name its own chart in `txt.fname`, so they *could* be paired — at the cost of opening every one during a scan. Worth doing only if a real library turns out to contain the case.)
- **The A–Z rail was built from the unfiltered library.** Under "No music" it offered letters with nothing behind them, and pressing one silently did nothing — which on a remote cannot be told apart from a broken button. It is built from the same filtered list a letter jumps into.
- A comment still described the old containment rule for titles, which is exactly how an unsafe behaviour gets restored later.

**And `PreviewLevel` was dropping bytes**, found by writing the processor-level tests Copilot asked for rather than by the review itself. Two places, both from the same wrong assumption — that an input buffer is always a whole number of frames:
- The analysis phase rounded down to whole frames and then **dropped the remainder**, because nothing returns to collect it.
- The write path stopped at `remaining() >= 2` and **discarded a trailing odd byte**.
Real PCM arrives frame-aligned so neither fired in the player, but a component that loses a byte on an odd-sized buffer is one bad assumption away from white noise. It now takes everything offered and keeps the low half of a split sample until its other half arrives. The test that found it asserts the property directly: **the same audio through the same processor gives the same bytes whatever size the input buffers are cut to.**

**The last two, and the card settled both** (Copilot on PR #2, 2026-08-26). No new inline comments; two carried over from earlier passes, and each was answered by looking at the real library rather than reasoning about it.

- **Only `[DUET]` comes off a title, not every square bracket.** Stripping them all looked equivalent and is not: it makes "Song [Live]" equal to "Song", and that comparison decides whether a chart may *replace* another — so a live recording could be downloaded against a studio chart's timing and the original folder deleted. **Measured across every chart on the card, `[DUET]` is the only square-bracket tag in any title**, on four songs; one of them, "A Whole New World (Album Version) [DUET]", carries a round bracket too and proves the distinction is real rather than theoretical.

The folder name and then the chart's document id break it, and the KDoc's promise of a stable order is finally true rather than aspirational.

**Previews are levelled, and the measurement said something surprising** (`audio/PreviewLevel.kt`, 2026-08-24). Reported as previews starting loud and dropping a second or two in.
- **The files do not do that.** Five real iTunes previews measured with `ebur128`: the first two seconds are within a decibel of the rest, and mostly *quieter*. So the drop is not in the content — it is the Shield or the television reacting to a new stream, and the thing to check there is the TV's own volume levelling.
- **What is real is the spread between songs: −9.3 LUFS ("Yellow") to −17.9 ("Billie Jean"), 8.6 dB.** That is the difference between uncomfortable and inaudible, one card to the next.
- **It listens before it decides, rather than riding the gain.** A compressor that follows the audio has exactly the failure the user described — a level you can hear moving. So the first 300 ms is held back, measured once, and everything including the held audio is played at that one gain, which never changes. Sound starts 300 ms later; it is right from its first sample.
- **It only ever turns down.** Only the opening is measured, so any amplification would eventually square off a louder chorus. Attenuating to the quiet end equalises just as well and cannot clip.
- **Never put it on `SongPlayer`.** It delays audio by 300 ms and the whole game rests on a measured 127 ms round trip; that path takes pass-through processors only. It also *bows out* rather than throwing on an unexpected format — unlike `SpectrumTap`, because an unlevelled preview is a far better outcome than one that will not play.

**Input latency: the two problems wearing one coat** (reported from the sofa 2026-08-22 as "missing the first part of notes" and "the arrow feels sluggish", then measured):

The report was one complaint and the causes were unrelated — one in scoring, one in drawing. Neither was the 40 ms display lead, which was the first suspect and was innocent.

- **The measuring came first, and it is repeatable.** Throwaway JVM harnesses fed `PitchTracker` synthetic notes with realistic attacks and reported how many milliseconds after a note truly starts the first voiced reading's window centre lands. That number is what the calibration compensates, so *anything above it is lost points*. Then the same question was asked of the real library: 76 charts pulled off the card, median beat **53.6 ms**, median note **3 beats (~161 ms)**, and **36.6 % of all notes are 1–2 beats** — which is why tens of milliseconds matter here at all.

- **The scoring half was the loudness gate averaging the whole window.** A 2048-sample window that is half silence reads as half as loud, so a note's attack was thrown away:

  | uncompensated lag | beats lost across the library |
  |---|---|
  | 0 ms (gate 0.01) | 0.0 % |
  | 21 ms (gate 0.06, 40 ms attack) | 3.6 % |
  | 64 ms (gate 0.06, 80 ms attack) | **25.9 %** |

  A soft-attack singer was losing a quarter of every beat, and **a quiet singer was detected never at all** — their whole note sat under the gate. Both fixed by two changes to `PitchTracker`, and it took both: measuring the level over **the newest slice only** while YIN still sees the whole window fixes a 40 ms attack but does nothing for an 80 ms one, because there the *threshold* binds rather than the averaging.

- **So the gate now has two heights** — clear `minLevel` to *begin* singing, only `holdLevel` (half) to *carry on*, expiring `holdSeconds` (150 ms) after the last voiced window. Measured on a four-note phrase, per-note onset lag fell from +56…+107 ms to +17…+47 ms. **It does not weaken crosstalk rejection**, which is the whole reason the gate is 0.06: the lower gate is only ever *held open* by this singer, so a voice heard across the room still never opens it. Pinned by a test named for that, plus its control.

- **None of it invalidates the 127 ms calibration.** `LatencyProbe` is a rising-edge detector (`voiced && !wasVoiced`), so the measured round trip already contains the pipeline's onset lag for a loud, instant-onset *tone* — 34.7 ms, which is the floor and is compensated exactly. What was never compensated is the extra that a *voice* costs over a tone, and that is what these changes remove. A calibration tone detects at +34.7 ms before and after.

- **`Int.MAX_VALUE + 1` is negative, and `coerceAtLeast(0)` made it worse.** The hold counter starts at `Int.MAX_VALUE` so a cold tracker has to earn the higher gate; incrementing wrapped it to `Int.MIN_VALUE`, which the guard then clamped *up* to 0 — reading as "sang a moment ago" and handing a fresh tracker the **lower** gate, precisely backwards. Caught only because a test asserted the crosstalk case. It saturates now.

- **The display half was three times bigger than the detector's, and it is what the eye actually sees.** Median-of-5 cost **64 ms** before the arrow began to move at all (a median of N only follows a step once (N+1)/2 of its samples are new), and `ArrowMotion`'s easing brought the total to **150 ms** to reach the new note. Median went to **3** and the easing and opacity fade were stripped entirely. **Both later came back** — see the 2026-08-26 section below, which is where the shipped numbers are.
  - **The arrow was arriving after the score, which is the thing that makes a game look like it is guessing.** The scorer reads the raw pitch and the arrow read a smoothed one, so a note lit up 83 ms — one and a half beats of a slow song — before the arrow was drawn inside it. Adding an onset grace on top would have made that worse, which is what the user spotted before it shipped. Measured chain: 150 ms (median 5, ease 0.05) → 83 ms (median 3, ease 0.03) → 33 ms (median 3, no easing).
  - The easing is kept and still tested, because the argument for it was real — raw YIN on a held voice wanders. If it returns it should return as a *small* number. **The median stays**, at one hop (21 ms): its job is killing lone wild readings, and with no easing behind it a single outlier would otherwise throw the arrow across the track for a frame.
  - **`MAX_STEP_SECONDS` had to come down with it**, and this is the trap: it is the clamp that stops a rendering hitch teleporting the arrow, and it only means anything *relative to the easing constant*. At 0.1 s against a 0.03 s ease it was more than three time constants — arrival, not a step. A test caught it, and the right fix was to tighten the clamp rather than relax the assertion.

- **The arrow is no longer drawn at the sing line, and that is the interesting one.** It shows pitch measured from audio that is already old, so drawn at the line it points at a note the singer has moved past — during a fast passage a *different* note, which quietly breaks the one thing the drawing promises: that an arrow inside a bar means that beat was paid for. It is now drawn at the moment in the song its reading actually came from, a little to the left. The sparks and the octave-folding reference move with it, so they now agree with the scorer better than they did.
  - **Every term is derived, not dialled in** (`GameSession.arrowLagSeconds`): capture latency (the reading describes its window's centre) + display lead (the notes are already drawn that far ahead, so the arrow is that much further behind them) + the median's own delay. About 83 ms, ~3 % of screen width.
  - **`ArrowMotion`'s easing is deliberately excluded.** It is the one term that is not fixed — it depends on how far the pitch just moved — and compensating a variable delay with a constant offset would be wrong in both directions instead of one.
  - The lag is read **per frame**, not baked into `TrackGeometry`, because it depends on the display lead, which is a live setting.

**The run-up to a note, and reading a television with a ruler** (reported from the sofa 2026-08-22 as "not registering until midway through the first note of a group", with a four-minute recording of Space Oddity):

- **The report was confirmed from the recording, and the phrasing was the clue.** *First note of a group* is precisely the case the two-height gate cannot help: within a phrase the lower gate is already open, but a phrase's opening note has to clear the higher one from cold. Space Oddity is the worst case for it — beat 55 ms, median note 358 ms, soft attacks throughout — so "halfway through" is about 180 ms, which is the detector's cold-start cost plus a singer sliding into the note.

- **Two causes, one symptom, and the fix deliberately addresses neither directly.** A note takes real time to *become* a pitch: a voice has an attack before it has a fundamental, singers scoop into notes rather than arriving on them, and YIN needs a window of audio before it will name one. `ScoringConfig.onsetGraceSeconds` gives back the beats between a note's start and the moment the singer landed it — so it does not care *which* of those causes ate the beats.
  - **It is 65 ms because that is the measured debt, and it started at 150 ms because that was a guess.** The user pushed back on the first version with exactly the right question — *is this just an artificial boost to mask our inaccuracies?* — and it partly was. 65 ms is the worst case of the lag the 127 ms calibration does not already remove; everything past it was forgiving the singer's scoop, which is difficulty rather than a fix, and difficulty belongs in `toleranceSemitones` where it is **visible** as taller note bars.
  - **Capped at half of each note** (`maxGraceShare`), so you always have to sing at least half a note to be given all of it. Without it a short note sits entirely inside the window — a third of the library is one or two beats long — and catching only its last beat would hand over the whole thing. Inert at 65 ms and load-bearing the moment anyone raises the grace, which is why it is pinned by a pair of tests that differ only in the cap.
  - **All or nothing, measured to the beat actually landed.** Forgiving whatever falls inside the window regardless of when the singer arrived would pay a genuinely late entry for the beginning of a note they were nowhere near.
  - **Only on a note's first hit**, so somebody who lands a note and then drops out of the middle of it is not handed the hole back. That is not the detector catching them out; they stopped singing.
  - **It cannot change what a song is worth**, which is the property the whole per-beat design exists to protect. `NoteScore.creditOnset` moves `beatsHit` and never `beatsScored`, and a test asserts the maximum is identical across a perfect, an early, a late and a silent performance.
  - `sungMidi` is left as recorded. A back-filled beat is one the singer is not being *charged* for, not one they are pretended to have sung.

- **The arrow's offset was right and looked wrong** — reported as feeling "very strange" and "detached". `GameTheme.judgedBand` shades the span between the arrows and the sing line, which turns a gap into a region with a meaning: everything inside it is in play. The offset is honest — that is where the audio being shown actually came from — and the shading is what makes it legible instead of arbitrary. The user's suggestion, and better than the alternatives of hiding the offset or reverting it.

**Measuring a television with a camera, when the framebuffer is not available:**

The flashing bug was diagnosed with `screenrecord` because the question was what the app *drew*. Here the question was what the app drew *while somebody sang*, which no framebuffer capture can answer — so it had to be a phone recording of the TV, with all the optics that implies. What made it measurable:

- **Calibrate scroll speed by cross-correlating the lyric band between two frames**, rather than trying to identify note edges. 371 px per 0.5 s here. It cross-checked exactly: 742 px/s × the 2.25 s window = 1670 px of track, which put the detected sing line at precisely the 30 % playhead. Two independent numbers agreeing is what makes the rest trustworthy.
- **Find the sing line by column brightness *below* the notes**, where nothing else is drawn, and check it at several heights — a TV shot at an angle can be keystoned, and a slanted line would invalidate every horizontal measurement. This one was vertical to the pixel from y=720 to y=990.
- **Do not trust absolute colour.** An OLED shot off-axis has a strong left-to-right brightness gradient, and the camera crushed red to zero on every blue thing on screen, so `noteIdle` and a hit fill could not be told apart by a fixed threshold. What survives is *adjacent* comparison: a 2.5× drop between neighbouring pixels of the same bar is a real fill boundary, the same drop across half the screen is the panel.
- **Take the maximum down a column, never the mean.** Averaging a 45-row band to find a 6-row-tall note dilutes it below any threshold — the first pass found nothing at all for exactly this reason.
- **One frame cannot tell a systemic lag from a note the singer missed.** Across 96 frames the gap between the fill and the sing line ran from −11 ms to +647 ms, which is the answer: it is not a constant offset, it is notes being credited late and intermittently.

**Sensitivity is asked once per mode, and the arrow keeps exactly one filter** (2026-08-22, after three measured runs of Space Oddity):

- **One microphone gate could never serve both modes.** Alone, the only competition is the song coming back off the television; with two singers each mic also hears the other person, and loudness is the only proxy these mics give for which mouth is nearest. `GameSettings` now keeps `soloMicThreshold` (default **100 %** sensitivity) and `duetMicThreshold` (default **75 %**, which is where the single shared value had been tuned), and `micThresholdFor(playerCount)` picks. The claim screen uses the same call, so a microphone is claimed on the terms it will be scored on. Measured on a real run: the old shared gate lost **17 %** of beats to "too quiet", the solo setting loses **3 %**.
- **Four settings with a paragraph each ran off the bottom of the television**, taking the footer with them — the exact fault that made UltraStar Play unusable. The explanation is now shown **only for the focused row**: one at a time, so the screen is a constant height however many settings there eventually are, and an explanation for a control nobody is touching was noise anyway. Verified on the device with the *last* row focused, which is the worst case.
- **The arrow ended up with a median of 3 and nothing else** (superseded 2026-08-26: it now has a median of 3, a 20 ms position ease and a separate 130 ms ease on the *lean*)**.** Easing and the opacity fade were stripped entirely to see the detector unadorned; the arrow jittered, and the median went back rather than the easing. The reason is that they fix different faults: easing is cheaper in lag (17 ms against 33 ms measured end to end) and cannot fix spikes — it only slows a wild reading down, still travelling most of the way there. A median discards the outlier outright, and being a median rather than a mean it does not drag a held note off its pitch. **The fade came back too**, once measurement showed it costs the arrow's *position* nothing: it decides whether the arrow is drawn, never where.

**Where the score actually goes, and when to stop optimising** (`score/ScoreDiagnostics.kt`):

- **Three levers were guessed at and two turned out to be spent**, which is why this exists. It splits every missed beat into too quiet / no reading / no period / near-miss confidence / off pitch, and reports what a wider tolerance or a lower confidence floor *would* have scored. Logged once per song on the `Gameplay` tag; nothing extra is captured during play, because `NoteScore` was already keeping the pitch sung at every beat for exactly this distinction.
- It retired `minProbability` as a suspect in a single run: of 244 no-pitch beats, **22 were recoverable at any floor** from 0.80 down to 0.60. That change would have felt obviously right and bought 1 %.
- **The singer's own variance is about 4 points**, measured as 67 % → 71 % across two runs with no scoring change between them. That is the resolution limit of every experiment done by singing, and it is what rules out the remaining levers: extending the onset grace to cover scoops is worth ~3 points, which cannot be told from noise.
- Space Oddity went **64 % → 71 %** across the session, all of it from fixing real faults. What remains is ~11 % of beats with no periodic signal in them (consonants, breath — there is no pitch in a `t` to find) and ~11 % genuinely off pitch at a median of 1.75 semitones. `toleranceSemitones` stays at **1.0**: the user's call, on the grounds that a game returning 90 % for a good-but-imperfect performance has nothing left to reward.

**The arrow tilts, and what the Karaoke Revolution clip actually shows** (2026-08-23):

- **`tiltDegrees` pivots the arrow about its tip**: flat angles it up, sharp angles it down, proportional to the error and saturating at `GameTheme.arrowMaxTiltDegrees` (34°) at `arrowFullTiltSemitones` (3). Level during a rest — with no note under the arrow there is nothing to be off *from*, and a tilt held over from the last note is advice about a note that has gone.
  - **Two sign conventions stack here** and are pinned by tests: screen rotation is clockwise-positive because y runs downward, and the arrow's body sits to the *left* of its pivot, so a positive angle swings the tail up and leaves the arrow pointing down. Invisible in review, obvious on a television.
  - Full deflection is tied to 3 semitones rather than to `toleranceSemitones`, so the tilt is still growing across the range a singer corrects over. Tied to the tolerance it would slam to maximum the instant a note was missed, which says "wrong" rather than "wrong by this much".

- **Measured against the reference clip** (`ffmpeg`, frames magnified 10× — the same filmstrip method as the flashing bug and the tall-button bug):
  - **Direction confirmed.** A red arrow sitting below the bar angles *up* toward it. Flat points up.
  - **The pivot is not the tip.** In the clip the arrow's body sits at the singer's pitch and the tip reaches up to *touch* the bar, which reads as rotating about the tail. Ours deliberately does not: our tip marks the pitch that is actually scored, and "the arrow is inside the bar" is meant to be the same statement as "this beat counts" — pivoting at the tail would swing the tip off the scored pitch and quietly break that. Their arrow carries no such meaning and can afford to aim.
  - **Maximum tilt reads at about 26°** on a badly-off note, against our 34°.
  - **The arrow is colour-coded by accuracy** — green on pitch, amber off, red badly off — which is doing much of the work the eye picks up, and which we do **not** have. It cannot be copied directly: our arrow's colour is *which singer it is*, and in two-player that is the only thing telling two arrows on one track apart. Options if it is wanted: drive saturation rather than hue, lean on the sparks (already an on-pitch-only signal), or accuracy colour in one-player only — the last being honest but making the arrow mean different things in different modes.

**Sync calibration harness** — `assets/calibration.{wav,txt}` is a real UltraStar song of 16 tones at exactly 1.0–16.0 s, alternating A4/E4, generated and verified to the millisecond. Uncompressed **on purpose**: an MP3/AAC decoder's priming delay would land in the measurement and be indistinguishable from real output latency. Point a mic at the speaker and the mic hears the song itself, so the lag from a tone's written position to its detection *is* the round trip. `diagnostics/SyncCalibrationScreen.kt` loops it, adopting the measurement at the end of each pass and scoring the next one with it — a correctly calibrated system scores near 10000, because the "singer" is the song, exactly on pitch and in time.

**The "flashing" was a one-frame backwards jump in `SongClock`, and finding it needed the framebuffer.** Reported as notes and lyrics briefly doubling. Two rounds of logcat said rendering was clean, and it was — the bug was in *what* was drawn, not how. `adb shell screenrecord` captures the framebuffer directly, which rules the TV and the camera out of the picture; then:

```
ffmpeg -i rec.mp4 -vf "crop=iw:ih*0.28:0:ih*0.72,tblend=all_mode=difference,signalstats,\
metadata=print:key=lavfi.signalstats.YAVG:file=diff.txt" -f null -
```

prints a per-frame difference, and the frames with the largest values are the anomalies. Extracting those as a filmstrip (`select='between(n,912,917)',tile=1x6`) showed the song jumping **backwards ~0.2 s for exactly one frame**. Cause: ExoPlayer occasionally reports a position a few hundred milliseconds behind, and `SongClock` only ignored backwards corrections *smaller* than a quarter of a second — anything larger was assumed to be a real seek and adopted. It never is: seeks arrive through `onPositionDiscontinuity` → `reset`. **Use this method before believing any theory about a visual glitch**; it distinguishes what the app drew from what the television did to it.

**Rendering is smooth in steady state, and the jank that exists is all at startup.** Measured with `adb logcat | grep -E "Davey|Skipped"`: over three minutes of play, **4 jank events, all within the first 15 seconds**, then nothing. The startup cost is one ~1 s stall as the song loads — `GameSession` builds ExoPlayer, enumerates USB, and measures every syllable in the song, all on the main thread during composition. Worth fixing eventually; it is not what anyone sees mid-song. **No GC events at all**, so allocation is not a problem. Use this method before believing any report of stutter — it distinguishes dropped frames from things that merely look like them.

**Measured CPU: 39–41% of one core without video, 52–55% with it** (both mics capturing + pitch + the full gameplay UI drawing at 60 Hz). That is *less* than the diagnostic screen it replaced, because the game draws in a single `Canvas` and only recomposes the score readouts when the number changes, rather than rebuilding a column of `Text` every frame. Video costs about 13 points on top of that — cheap, because the Shield decodes it in hardware — and still leaves three cores idle.

**Earlier CPU baseline** (both mics capturing + pitch + the diagnostic screen): 72–76% of *one* core of four. Split per-thread, roughly 60% of that is the two capture/pitch threads and 40% is the diagnostic UI redrawing. So pitch detection for two mics costs ~45% of a core. Fine as-is, but it is the number to re-check once video playback and the real gameplay UI are added. **If it ever needs to come down, the lever is downsampling before YIN** — voices top out near 1200 Hz, so 48 kHz is enormously oversampled for this; decimating to ~12 kHz shortens both the window and the lag range for roughly an order of magnitude less work. (An FFT-based difference function is the other option, but a bigger change for less gain.)

- **Song video** (`game/SongVideo.kt`) — the promised background video, delivered.
  - **Its own player, muted.** The obvious approach — play the `.mp4` and take its audio too — would quietly invalidate everything: the notes are timed against the `.mp3` and the 127 ms round trip was measured against that path, while a video file's audio is often a different master with a different offset. The mp3 stays the single source of both sound and truth.
  - **`#VIDEOGAP` is in seconds while `#GAP` is in milliseconds** — an inconsistency in the UltraStar format itself. The metadata field was called `videoGapMs` right up until video was wired, which would have put every video out by a factor of a thousand. Now `videoGapSeconds`.
  - **Not one song on this card declares `#VIDEO`**, though several ship an `.mp4` beside the `.txt`. The scanner falls back to any video file in the song's folder — a folder holds one song's media, so a lone video in it is not ambiguous, and requiring the header would have shipped a feature that never fired on the real library.
  - Drift is corrected only past 0.4 s and only every 250 ms. The video is decoration: nobody sees a tenth of a second of lip-sync error on a music video, and every correction is a visible seek, so correcting little and late looks better than tracking well.
  - **Full brightness, with contrast coming from panels behind the UI** (`GameTheme.trackBackground`, `chipBackground`). Dimming the whole video to protect a strip of text was the first attempt and it was backwards: it spent every pixel of the picture on a problem that only exists where the text is.
  - **`Modifier.requiredSize`, never `Modifier.size`.** (Cover itself was removed on 2026-08-26 — see below — but this rule still applies, now to holding an exact aspect ratio.) This is the whole reason cover never worked. `size` is *clamped by the incoming constraints* — that is its documented difference from `requiredSize` — so a view deliberately sized past the screen edge, which is exactly what covering means, silently snapped back to the screen. A `TextureView` stretches its content to whatever bounds it ends up with, so **every video was being squashed to 16:9**: a 4:3 file came out stretched wide, a 2.35:1 file came out tall and thin. The letterbox crop could not work either, since it multiplies a size that was being clamped away. Caught by logging requested vs actual size — `asked=1000.8dp got=1920px` — not by reading the code, which looks right.
  - ~~**Black bars are measured off the picture, not inferred from the aspect ratio.**~~ **Removed 2026-08-26** — `measureLetterbox` no longer exists; the bars are filled with an ambient wash instead. Kept because the *measurement* here is still the correct answer if cropping is ever wanted again. A 2:1 image encoded into a 16:9 file carries its bars inside the frame and every dimension the player reports still says 16:9 — pixels are the only evidence. `measureLetterbox` samples the frame at 128×72, finds the dark margins and crops them away, refusing to act on an all-black frame (that is a fade, not a letterbox) and never cropping more than 1.5×.
  - **Six samples, and the smallest crop wins.** A bar is in every frame of the file, so a real one survives every sample; a dark sky at the top of one shot does not, and taking the first answer would zoom the whole video for the rest of the song on the strength of it. A line counts as bar at **97 % dark rather than 100 %** — compression leaves noise where a bar meets the picture, and one stray bright pixel was enough to hide a band 130 pixels thick.
  - A `TextureView`, not a `SurfaceView`: filling the screen means sizing the view past the screen edge, and a SurfaceView is a separate compositor layer that is not reliably clipped by its parent.

**What is actually in this library's videos** (measured 2026-08-16 with `ffmpeg cropdetect` over 15 of the 46 files, not guessed):

- **Most are 4:3 standard-definition rips** — 640×480, 720×480, one 600×480 — not 16:9. That is why the squashing was so visible: nearly every video was being stretched sideways.
- **About half carry black bars inside the frame.** Worst cases: 1920×1080 files holding a 1920×804 picture (2.39:1, 138-pixel bands top and bottom), and one holding a 1362×1080 picture (278-pixel bands at the sides). The needed crops are 1.34× and 1.41× — comfortably inside the 1.5× limit, which was chosen before any of this was measured and turns out to be about right.

**To check a video file, pull it off the card and use ffmpeg** — far faster than driving the TV:

adb shell "find /storage/5002-E7C7/UltraStar -type f -iname '*.mp4' -printf '%s\t%p\n'" | tr -d '\r'

- **Full-screen feedback visualiser** (`visual/`, `game/SongVisualizer.kt`) — for songs with no video, which is **25 of the 49 on the card**, not the handful it was when this was first built.
  - **It replaced a row of spectrum bars**, which were legible and completely uninteresting: they moved with the music without ever looking like anything, and they lived in the bottom half of the screen that the track already occupies. What was wanted was the other Winamp idea — MilkDrop.
  - **Frame feedback is the whole mechanism.** A low-resolution buffer (540 lines) redraws *itself* every frame slightly moved and slightly darker, and the current instant of sound is drawn on top. The trail is the picture; the waveform is only the pen. One shader does the moving, and what separates a tunnel from a plume from a churn is nothing but *how* the previous frame's coordinates are wrong.
  - **This is why it had to be OpenGL.** Compose's `Canvas` cannot sample the frame it is drawing, and `RuntimeShader` is API 33 against this device's API 30. `visual/VisualizerView.kt` is a `TextureView` with its own EGL context and render thread — a `GLSurfaceView` is a compositor layer punched *behind* the window and the track and scores have to draw over this.
  - **No third-party visualiser, and the licence is why.** projectM is the obvious candidate — the open-source MilkDrop engine — and it fails two of this project's rules at once: LGPL rather than permissive, and not on Maven Central, so it would mean vendoring a large C++ library plus thousands of preset files of assorted provenance. What is here is a few hundred lines of GLSL that belong to the project.
  - **Sixteen presets in `visual/Preset.kt`, and every field but the wave style is a plain number.** That is what lets one preset *become* the next over four seconds by interpolating each one, instead of cutting between them — the same trick MilkDrop uses, and most of why it never looks like a slideshow. They are chosen to differ from each other rather than to each be clever; sixteen variations on one idea would be the bar-graph complaint again.
  - **The order is load-bearing, because each preset melts into its neighbour.** The second eight are woven in among the first eight rather than appended: appending would have made the back half of the cycle a distinct second act, and would have put similar looks next to each other where the blend is most visible.
  - **The cycle starts on a random preset, and adding presets is what forced that.** Sixteen at 26 s each is a seven-minute pass against a three-minute song, so a fixed start meant the back half of the list was never seen by anybody. One random index costs nothing and makes every preset equally likely while keeping the deliberate ordering.
  - Two wave styles were added with them — **ROSE** (a flower; the only path whose *silhouette* changes as it breathes, so petals thicken on the beat instead of the whole shape scaling) and **LISSAJOUS** (the only path that crosses itself, so the additive blend leaves a moving bright knot where the strands meet). LISSAJOUS is also the only one whose normal comes from the tangent rather than the radius: there is no centre for it to point away from.
  - Colours deliberately avoid the game's cyan and pink. The track and the arrows own those, and a background in the same two colours makes the one thing that has to be *read* harder to find.
  - The waveform is drawn as a **triangle strip, not `GL_LINE_STRIP`**: line width above one pixel is optional in GL ES and widely ignored, and a hairline is not a look. Two vertices per point either side of the path gives a ribbon of any width.
  - `SpectrumTap` now also publishes a **waveform** (256 points, decimated from the analysis window), **bass and treble levels**, and a **beat count**. The count is a monotonic counter rather than a flag because a renderer at 60 fps and a detector at 47 updates a second cannot agree on "is there a beat right now", but they can always agree on how many there have been. A beat is bass louder than bass has recently been — a ratio, not a level, because a quiet song has quiet beats.
  - **Measured 52% of one core**, which is the same as playing a hardware-decoded video and about 11 points above a plain background. Three cores still idle.

- **Spectrum bands** (`audio/Fft.kt`, `audio/SpectrumTap.kt`) — the original radix-2 FFT, still what drives the visualiser's motion. Original radix-2 FFT (`audio/Fft.kt`) fed by a Media3 `AudioProcessor` that taps the song **pass-through**: it is the same audio the singers are scored against and the one thing it must never do is change it. Android's `Visualizer` effect was the alternative and needs `RECORD_AUDIO` — an alarming permission to ask a family for so that bars can wiggle, and unnecessary when the audio already passes through this app.
  - Bands are **log-spaced and tilted upwards** (~+3 dB/octave). Drawn honestly a spectrum is a cliff of bass and a flat line everywhere else, because that is genuinely where music keeps its energy; every visualiser ever built compensates.
  - **Entirely automatic, per song, with nothing to configure.** The scanner resolves a video for every song (header, else any video file in its folder); no video means the visualiser, and a video that turns out not to *decode* also falls back to it. Adding a song without a video needs no action of any kind.
  - The tap is therefore fitted to every song — it has to go in when the player is built, before anyone knows whether the video works — but it does no work until the visualiser switches it on, so a song with a working video pays nothing.

**A finish flag must be a latch, not a mirror.** The missing results screen was this: finishing pauses the player, pausing freezes the clock, and the frozen position then reads as *not* finished — so tracking the condition in both directions cleared the flag on the very next frame and left the song paused with no score on screen. It had been appearing for exactly one frame. Related and also real: a chart can outlast its own audio ("Steve's Lava Chicken" ends its last note 0.3 s after the recording stops), so `isFinished` checks the audio running out as well as the notes.

- **Pressing Play with no song folder asks for one** (`ui/FirstRunScreen.kt`). The app has only ever read the one folder it was pointed at — it has never searched the device, and searching a terabyte card for stray `.txt` files would be slow and still guess wrong. So there is exactly one thing it must be told, and the moment to ask is when somebody has just said what they want. It routes into the normal flow afterwards, and is never seen again once a folder is chosen. It doubles as the recovery path when a grant goes away with the card it described, which is indistinguishable from a first run and wants the same screen.
- **Rescan lives on the Songs screen only.** It was on the song picker too, which is the middle of getting a game started — the wrong moment to offer a five-second rescan, and a second copy of a control that now has a proper home.

**Gameplay enhancements** (2026-08-26, this branch — everything below supersedes the arrow, video and results notes above where they disagree):

- **The arrow's lean now eases on its own clock, and it is far slower than its position** (`ArrowMotion.tiltSecondsToSettle`, 0.13 s against the position's 0.02 s). They were sharing one time constant, which meant the tilt snapped: when the note under the arrow changes, the *target* angle moves by the interval between the two notes even though the singer has not moved at all, and at 20 ms that jump is instantaneous. Reported from the sofa as jarring, and it was. **The position and the lean are answering different questions** — the position is a measurement, where every millisecond of lag is the instrument lying, and the lean is advice, which cannot be useful and change six times a second.

- **The median is back at 3, and it costs no apparent lag.** The note above claiming it lags the score is arithmetic that no longer holds: `arrowLagSeconds` already carries `MEDIAN_LAG_SECONDS`, so the arrow is *drawn* 21 ms further left, which is where the audio it is showing actually belongs — and `drawHits` gates the note fill on the same instant (`arrowNow`), so the fill cannot get ahead of the arrow that earned it. Easing at any time constant still travels most of the way to a wild reading before turning round; only a median discards one outright.

- **The remaining jumpiness was the octave fold, and no amount of smoothing could ever have fixed it.** `foldToOctaveNear` moves the sung pitch into the octave nearest the note under the arrow, and *both* of its inputs cross the tritone boundary constantly: a voice sitting near a tritone from the note wobbles across it and the arrow teleports an octave and back, and a melody that leaps a fifth re-folds a completely steady voice and throws the arrow twelve semitones with nobody having sung anything. Those are steps in the *target*; easing only draws a teleport more slowly. There is now a **1.5-semitone hysteresis band** — the fold prefers the octave the arrow is already in unless the alternative is more than that much better. Pinned by `OctaveFoldTest`, which names both failure modes.

- **The results no longer arrive the moment the last note does.** `GameSession.isFinished` now waits for the *recording*, and `isVocalFinished` covers the stretch in between. Cutting to a scoreboard mid-guitar-solo reads as a crash; an outro is part of the song. A **"Skip to the end"** button appears bottom-right and takes focus once there is nothing left to sing, because by then it is the only thing on screen anybody can press. The centre key is let through to it — gameplay's preview handler would otherwise swallow it into a pause. The HUD is already fading out by then on its own (`VocalBreaks` sees the outro as a break like any other), so the offer sits over a clean video.

- **Songs are normalised to one loudness** (`audio/Loudness.kt`, `LoudnessScanner`, `LoudnessCache`, `GainProcessor`). The library is thirty years of rips and varies by more than 10 dB, which means reaching for the remote between every song.
  - **Measured, not guessed**: `MediaCodec` decodes five two-second windows spread through the file (never the first or last few per cent — songs fade, and a window of silence would make a normal record look quiet) and reports RMS and peak. Kept on disk by document URI. Unlike the song-library cache this one *cannot* go stale: a document URI names one file, and songs here arrive whole and are deleted whole.
  - **It runs during the title card**, which is the only free moment in a song, under a 2.5 s decode budget and a 1 s ceiling on top of that. Late is survivable because the gain ramps rather than steps.
  - **A processor, not `player.volume`, and that is the whole point.** The player's volume can only turn a song *down*, so normalising with it would pull the loud majority down to meet the few quiet ones and leave the entire evening quieter than the television was set for. `LoudnessEnhancer` would have done the job in ten lines and cannot be used: this Shield re-encodes to E-AC3 and system audio effects do not run on a direct stream. Inside ExoPlayer the samples are still PCM.
  - **An unsupported encoding passes through rather than throwing.** `SpectrumTap` throws `UnhandledAudioFormatException` for anything but 16-bit PCM, and in Media3 that is *not* opting out — `DefaultAudioSink` turns it into a `ConfigurationException` and the song does not play at all. It has never fired because ExoPlayer decodes to 16-bit by default, but trading every song for a level adjustment is not a bargain worth offering.
  - Target is **-13 dBFS RMS**, near the top of what this card holds, because aiming low just moves the problem to the remote. Boost is capped at 10 dB and further capped by the file's own peak headroom (+3 dB of overshoot, absorbed by a soft knee — quiet-with-transients is exactly the shape of an old rip, and one snare hit at full scale would otherwise block the whole normalisation). Plain RMS rather than K-weighted LUFS: the weighting matters between a podcast and an orchestra and moves a card of pop records by about the same amount each.
  - **Previews are levelled by `PreviewLevel`, not by this**, and the two must not be swapped. That one holds the first 300 ms back, measures it and picks one gain it never moves again — which is the right answer while somebody is browsing and the wrong one for a song, because 300 ms of delay in the player path would put every note out of time and invalidate the 127 ms calibration. This one measures the file *before* playback, so it adds no delay at all and can boost as well as cut. A first pass at normalising previews from here was written on this branch and dropped on merging main, which already had the better answer.

- **The video was shown whole with ambient bars for two days, and the cover crop is back** (superseded 2026-08-28 — see the next section). The wash was a good answer to the wrong question: the bars were what was being complained about, and filling them prettily is not the same as not having them. `AmbientWash` is gone; git has it.

- **The results screen is stars, not a percentage** (`starsFor`, `game/Stars.kt`). A percentage is precise and says nothing anybody wants to hear. Equal fifths, so four stars is a good performance and five is an excellent one — which is where real singers land, given the calibration harness scores 98 % and a person singing well scores about 70 %. **Zero stars only for zero**: the one person who never needs telling they did badly is the one who already knows. Taken from the **points** rather than beat accuracy, because the points already carry the golden notes and the line bonus, and stars disagreeing with the number beside them would be worse than either. The unearned stars are drawn as faint sockets, so three-of-five reads as three of five rather than as a smaller row.

- **A duet is one score.** `combined()` averages the two parts and sums their beats, so a duet is still marked out of 10000 and its stars mean what a solo song's do. Two scoreboards invite exactly the comparison a duet is not about — one part being shorter, lower, or the one carrying the harmony does not make the person singing it worse. **Versus keeps its two corners**, because there the comparison is the whole point. Averaged rather than summed weights each *part* equally rather than each beat, which is the honest reading: singing a short part perfectly is as much as anyone can do with it.

- **"Pick another song" is first and focused** on the results. That is what actually happens next almost every time, and on a remote the focused button is the one that costs nothing to press.

- **Points arrive as an animation, once per phrase.** The score walks up to its new value over 550 ms — a number that jumps by 240 between two frames is read as a *different number*, one that counts is read as points being earned — and a gold "+240" floats up beside it. **The batching needs nothing to know where the phrases are**: the score simply stops moving when the singing stops, so restarting a 260 ms debounce on every change *is* the phrase detector. A "+2" per beat would be a slot machine. The lane under each score is reserved whether or not anything is in it, or a gain would shove the top of the screen about once a phrase.

- **Encouragement per phrase, on the track** (`game/Praise.kt`). "Good / Nice! / Great! / Perfect!" by how much of a *lyric line* landed — a line is a phrase, which is the smallest thing a singer thinks of themselves as having got right, and it is already in the data since every `NoteScore` carries its line index. **There is deliberately nothing below "Good"**: a child having trouble can already see the notes going past unfilled, and the last thing a family karaoke game should do is confirm it in large letters. Two singers on one track get a side each. Colour climbs blue → green → gold with the rank, so the ladder is legible without reading the word. Pure and unit-tested, including that two lines finishing between two frames say one thing rather than stacking.

- **The results say when a record has fallen** (`settings/HighScores.kt`). The only thing in this app that remembers a *result* — everything else is deliberately forgetful, because remembering the wrong thing is worse than asking, and a record belongs to the song rather than to whoever is holding a microphone. **Duets are filed separately from individual scores**, since a duet is one pair singing two parts and an individual score is one person singing the whole thing; a shared table would let a duet quietly take the record for a song nobody has sung alone. Solo and versus share a table, because both are one person against the whole part. Equalling a record does not steal it. When nothing was beaten, the standing record is shown with its holder's name, which is what makes it worth beating.

**Four things from the first real evening of play** (2026-08-28, reported from the sofa):

- **The arrow was drawn 31 ms to the right of where its reading came from, and two of the terms had simply been missed.** Reported as the arrow feeling "a half step behind" and "not making proper contact with the notes at the proper time", **worst in fast songs** — which is the clue, because a fast song's beat is about 54 ms, so 31 ms is most of one. `GameSession.arrowLagSeconds` now carries two more terms:
  - **`READING_AGE_SECONDS` (11 ms).** `PitchTracker` publishes once per hop and the draw pass takes whatever the latest reading is, so at an arbitrary frame that reading is already half a hop old — *on top of* `captureLatencySeconds`, which describes only where the analysis window's centre sits relative to its end. It belongs to the arrow alone: scoring timestamps a reading on the capture thread when it is made, so it never pays this.
  - **`ArrowMotion.POSITION_SETTLE_SECONDS` (20 ms).** It was excluded on the argument that easing's delay "depends on how far the pitch just moved" and so could not be compensated by a constant. **That confused settling with delay.** The easing is a one-pole lag and a one-pole lag's delay *is* its time constant, whatever the input is doing, because the filter is linear. Settling time varies; delay does not.
  - **The test for belonging there is whether a delay hits the arrow and not the notes.** The frame period was nearly added and must not be: a frame is seen about half of one after it is drawn, but the arrow and the notes are drawn in the same frame and seen in the same instant, so it cancels out of the gap between them.
  - What this does *not* fix is the other half of the report. The arrow genuinely shows audio about 120 ms old and no amount of drawing can undo that; the levers on the real lag are the median (21 ms) and the easing (20 ms), and both were put there on purpose after the previous round of testing.

- **Display lead moving the arrow's distance from the sing line is correct, it surprised the user, and so the settings screen now says so.** The notes are drawn `displayLead` *ahead* so that they are right when the light reaches an eye; the arrow's data is real and old. By the time a frame is seen, that data is `displayLead + capture + median + easing` old, so the gap has to contain the lead. It cancels exactly out of `arrowNow` itself — which still comes to `songTimeFor(playerPosition) − medianLag`, the same instant the scorer used — so the lead changes **where the arrow is drawn relative to the notes and nothing about what it is worth.**

- **The cover crop is back, and it fades in from black** (`SongVideo`). The user's call, reversing the 2026-08-26 change; `measureLetterbox` is restored verbatim and `AmbientWash` is deleted.
  - **The zoom was the complaint, not the crop.** Bars can only be measured from real frames, so the answer cannot be known before the video starts — and the old version applied it as the evidence arrived, which is why the picture visibly zoomed a couple of seconds in, every song. Now the whole measurement happens **behind a black screen** and the picture fades up once the crop is settled, which hides the machinery completely.
  - **So the samples are packed rather than spread**: eight at 200 ms instead of six at two seconds — *more* evidence in an eighth of the time. Spreading them was never what the sampling needed; it was there because the result was being shown as it was gathered.
  - **Only readable frames count towards the total**, which is what makes packing them that tightly safe. `measureLetterbox` already returns null for a frame too dark to judge, so a video opening on a fade from black spends samples waiting rather than measuring the fade and cropping to it. A four-second deadline stops that becoming a black screen over a playing song.
  - It fades back to black over the last 1.2 s of the **video's** duration — videos are often shorter than their songs. The song's own end needs no fade: the results are already over the top of it.
  - Alpha is set on the `TextureView` itself rather than through a `graphicsLayer`, because a TextureView is exactly the kind of view where that distinction has historically bitten.

- **Difficulty is a setting now** (`settings/Difficulty.kt`): Easy 2.0, **Normal 1.5 (the new default)**, Hard 1.0 semitones. Hard is what the game was before there was a setting, so nobody who liked it has lost it.
  - **One lever, and it moves the picture with the score.** `ScoringConfig.toleranceSemitones` is also the drawn height of a note, so an easier setting has visibly fatter notes and "the arrow is inside the bar" stays the same statement as "this beat counts". Any future difficulty knob has to keep both reading the same constant.
  - **`onsetGraceSeconds` deliberately does not move with it.** That 65 ms is a measured debt this app owes the singer for its own detection lag, not generosity, and rolling a correction and a handicap into one control makes it impossible to say afterwards which of them a score came from.
  - Easy is capped at 2.0 because pitch classes are never more than six semitones apart: much past this it stops being forgiving and starts paying for wrong notes.
  - Named rather than numbered — "1.4 semitones" is not something anybody reasons about from a sofa — and driven with left/right on the existing slider row, indexing `entries` by ordinal. They are declared **easiest first** so the bar fills as the game hardens; a test pins that, because the screen depends on it.

- **A fifth setting pushed the footer off the television, and the answer is that the settings list scrolls.** The user’s rule, and it is the right one: **vertical scrolling is fine as long as it actually works; horizontal scrolling is not.** That is the distinction UltraStar Play failed — not that it had more settings than fit, but that what fell off the screen could not be reached. So the first fix here (tighter rows, and the hint moved up beside the heading) was only half of it: the tightening is reverted, and the rows now sit in a `verticalScroll`.
  - **The heading and its hint stay outside the scrolling part**, so the one line telling you how to work the screen can never be scrolled off it. That is also why the hint moved off the bottom — not to save space, but so it is anchored to something that does not move.
  - **A plain `Column`, deliberately not a `LazyColumn`.** A lazy list does not compose what is off screen, so there is nothing below the last visible row for the focus search to find and the remote simply stops moving — the same dead end a disabled TV button creates, and the trap the song picker and the add-songs list both document. Every row here exists, so pressing down always has somewhere to go, and Compose brings the newly focused one into view by itself.
  - **Verified on the television past two screenfuls**, by temporarily adding six probe rows: focus walked to the last of eleven, the list followed it, the heading stayed put, and nothing ran off the right edge. The probes were removed again. Five real rows barely scroll at all — which is exactly why it had to be tested with more than five, since "it fits" and "it scrolls" look identical when it fits.
  - The hint takes the leftover width rather than a fixed slot, so a longer one wraps to a second line instead of running off the edge. **Nothing on this screen may ever scroll sideways.**

**The song picker grew up** (2026-08-28) — records on the cards, controls across the top, letters across the bottom, and a row that joins end to end. Everything below was driven and screenshotted on the real television against the real 98-song card.

- **Each card carries the score to beat and who set it** — stars and a name under the artist. `starsFor` and `StarRow` are the same ones the results screen uses, so a five-star record on a card and five stars at the end of a song mean the same thing.
  - **Filed the way the game about to be played will file it.** Duets and individual scores are separate tables, so a card shows the record the person standing there could actually beat, not a number from a different kind of performance. That means the same song can show a different record with one singer and with two, which is correct rather than confusing: they are different contests.
  - **A record only ever names somebody the app still knows.** `HighScores.forget(name)` runs when a profile is deleted and `HighScores.rename(from, to)` when one is corrected, so records follow their owner and leave with them. `scoreIfKnown` is the guard in front of the display for anything that got past those — records written before they existed, or a prefs file from an older build. Without it a deleted name would sit on a card for ever, unbeatable by the person it belongs to and removable from nowhere. Verified on the television with a seeded record by a name that is not a profile: it does not appear.
  - The lane is reserved whether or not there is a record, so the row does not step up and down as it scrolls past songs nobody has finished.

- **Search, sort and filters run across the top; the letters run across the bottom.** The management grid puts its letters down the right-hand side because that grid fills downwards. This row fills across, so a rail at right angles to the thing it indexes would be a rail pointing the wrong way.
  - **The letters are built from the filtered list**, so a letter offered under a filter always has something behind it. Verified: filtering to Pop took the bar from twenty letters to fourteen.
  - **Sort and mode are chips; genre and decade open a list.** Two values and three are few enough that showing them all costs less than hiding them. Seventeen genres is not — a chip that steps to the next one on each press is seventeen presses to reach the wrong end of the alphabet.
  - **Those lists borrow the row's space rather than opening over it, and deliberately are not a `Popup`.** A popup is a separate window, and on a television that means handing focus outside this composition and hoping it comes back. Everything stays in one column, which is also why Back always has exactly one thing to undo.
  - **Mode is only asked with two singers.** On your own a duet collapses to a single line, so "duet or versus" is a question about a game nobody is playing.
  - **One Clear, not four.** Four filters cleared one at a time is four chances to leave one on, and a filter still quietly in force looks exactly like a library that has lost songs. For the same reason the count reads "23 of 98 songs" rather than "23 songs".

- **Genre is read as a list, because the field is written as one.** Four charts on this card say "Soundtrack, K-Pop"; read whole that is a genre nothing else shares and both of the genres it actually names go missing. **Spellings are folded, genres are not**: a hyphen becomes a space, so "Pop-Rock" and "Pop Rock" are one chip, and "Rock" and "Pop Rock" stay two. Deciding "Alternative" and "Alternative Rock" are the same genre is an opinion the person who wrote the chart did not share.
  - Offered **commonest first**, because a remote pays per press. Measured on the card: Soundtrack 24, Pop 20, then a long tail.
  - **Built from the library rather than from a fixed list**, which is the opposite of the call the add-songs screen made and for the opposite reason. That list has to keep its shape while search results arrive underneath it; this one describes a library that changes only on a rescan, and a fixed list would offer genres nobody here has while hiding the ones they do.

- **Decade is the filter that always works.** All 98 charts on this card carry `#YEAR` and only 72 carry `#GENRE`, and the years spread evenly: 1960s 4, 1970s 20, 1980s 17, 1990s 11, 2000s 5, 2010s 27, 2020s 14. A year that is not four digits is not a decade — "97" for 1997 happens, and filing that under the 1990s is a guess.

- **Searching uses the drawn keyboard, not Gboard.** Same reason as the add-songs screen, and more sharply here: Gboard covers the bottom two thirds of this television, which on this screen is every song card. The count updates as the letters arrive, which is what makes it safe to hide the cards while typing — the number says what is waiting behind. Title **and** artist, because half of remembering a song is remembering who sang it.

- **The row joins up end to end.** Running off the end of Z and being stopped dead is the row saying "no" to the one direction you were already travelling in; coming out at A says "that was all of them", which is the same fact and an answer rather than a wall. Only the two ends are intercepted — everywhere else the ordinary focus search does the work, and taking that over would mean reimplementing it.

- **A trap worth naming: two effects both wanted the first frame.** "Open on the song just sung" and "go back to the top when the sort or filter changes" both fire on the first composition, and the second runs later, so it silently overwrote the first every single time. The re-file effect now skips its own first run.

- **What a song with no cover shows** (the answer to a question, and it was already there): the first letter of its title, large, on the same panel a cover would fill. Enough to tell two neighbouring cards apart at a glance, and it is why "No artwork" is a filter on the management screen rather than a fault — a song without a picture is complete, just plainer.

**Reaching the picker from `adb` needs a temporary bypass.** It sits behind the claim screen, which waits for a real voice, so `Screen.Players` was pointed straight at `Screen.Picker` for testing and put back afterwards — the same trick as the probe rows on the settings screen. Worth remembering: it is the only way to see this screen without somebody singing.

**A microphone that "isn't being recognized", and it was never the microphone** (reported from the sofa 2026-08-29, diagnosed and fixed the same morning).

One of the two mics did nothing on the claim screen, and unplugging and replugging the hub did not help. It was not any of the gameplay changes — nothing on that branch touches `mic/`, `cpp/`, `pitch/`, `MicClaim.kt` or `ClaimScreen.kt`. `dumpsys usb` settled it in one read:

```
alsa_manager={ ... address=/dev/bus/usb/001/017 ... address=/dev/bus/usb/001/016 }
permissions_manager={ device_permissions={ device_name=/dev/bus/usb/001/017  uids=10101 } }
```

Both mics enumerated perfectly — `046d:0a03`, endpoint `0x82`, 208-byte packets, the lot — and the app held a USB permission grant for exactly **one** of them. A `uiautomator dump` found the other one's permission dialog still on screen, unanswered from the night before; pressing OK started it capturing immediately.

- **An Android USB grant is keyed on the device *path*** (`/dev/bus/usb/001/016`), which is handed out afresh on every enumeration. So every replug, and every reboot, invalidates every grant — **replugging is what causes this, which is why replugging could not fix it.**
- **The bug was asking for both at once.** Two requests put two identical system dialogs on top of one another. Somebody answers the one they can see, the second is never mentioned again, and the app is left with one working microphone and one that looks broken — on the one device where "the microphone is broken" is a conclusion everybody is already primed to reach. Permission is now asked for **one microphone at a time**: `UsbMicSession` holds `asking` (a port, not an index, because the list renumbers on every hot-plug) and starts the next request only when the previous one is answered. `asking` is cleared before anything else can return early, and cleared again if that mic is unplugged while its dialog is up — otherwise one dismissed dialog would strand every microphone queued behind it.
- **A refusal was a dead end, and that was the worse half.** Nothing re-asked, and nothing on screen said why: `ClaimScreen` never read `OpenMic.status` at all, so a refused mic sat in the list with a silent meter, indistinguishable from a dead one. There is now `MicState` — an enum, because screens have to *act* on this and matching on prose stops working the day somebody rewords a message — plus `usableMics`, `refusedMics` and `askAgain()`.
- **The claim screen is where a refusal is resolved, and the screens before it deliberately do not know about it.** Gating the main menu and the singer count on *usable* mics was the first attempt and it was wrong twice over: it made "Two singers needs a second microphone. Only one is plugged in" into a lie told to somebody looking at two microphones, and — much worse — with both mics refused it disabled Play, which is the only route to the button that undoes it. Those screens count what is **plugged in**, exactly as before. The claim screen blocks only when the refusal actually matters (`usableMics.size < playerCount`), so a spare nobody allowed is not a warning, and it says what is wrong, hides the meter that cannot move, and puts "Allow microphone" first with the focus on it.
- **`askAgain` starts what is already allowed as well as asking for what is not.** Re-asking alone leaves a microphone that somebody granted from elsewhere sitting silent for ever, because there is nothing left to ask it. `startGranted()` is shared with `refresh()`, which is also why a relaunch needs no dialogs at all.
- `OpenMic.state` is Compose state rather than a plain field: the offer has to appear and disappear on its own. Only the main thread writes it — the broadcast receiver and the hot-plug refresh — so no capture thread races a redraw.

**A USB grant cannot be revoked from `adb`**, which is worth knowing before trying: there is no `cmd usb`, the Shield is not rooted, and the only things that clear one are a physical replug or uninstalling the app — and uninstalling would take the SAF folder grant, the profiles and the high scores with it. So the queue itself is verified by construction and by the one-at-a-time logs; the *screen* was verified with a temporary probe forcing one mic into `Refused`, which found a real bug in `askAgain` before it shipped. Probe removed; the same trick as the settings screen's extra rows.


**The first-release pass** (2026-08-30). Ten changes across six screens, asked for together before an alpha.

**Driven on the real television and the real 98-song card**, except where it needs a voice: the menu title, the Settings exit (including that pressing up from the first dial reaches it), the claim screen in both one- and two-singer form with two microphones attached, the keyboard on both screens that draw one, the cursor keys and forward delete, infinite scroll, back-to-the-top after a search, and fuzzy matching. **What still needs somebody to sing** is the claim itself — whether 0.9 s of held voice feels right, and whether the spotlight-and-raw-level handover reads the way it should — and everything downstream of it.

Two things were confirmed by measurement rather than by eye: typing **"ALADIN"** (one letter short of Aladdin) returns all three Disney's Aladdin songs out of 98, where plain containment returned none; and the results grid, scrolled deep enough to have paged twice ("showing 62"), goes back to the top the moment a new search lands.

- **The main menu says "UltraStar Android TV" rather than "Sing".** It is the one screen that is ever seen cold, by somebody who did not install the app.

- **The lone singer is purple** (`GameTheme.soloPlayer`), on the claim screen and in the game alike. It was green, matching the start of the arrow's accuracy scale — but the arrow is accuracy-coloured on its own when solo, so the green was never reaching the arrow; it was colouring the notes, the name and the score, which are exactly the things that should say "there is one of you". The claim screen now asks `playerColor(slot, solo)` instead of indexing `playerColors`, so a solo singer is no longer told they are player one in player one's colour.
  - **Two players keep cyan and pink.** That pair is the only thing telling two arrows on one track apart, and it was chosen to survive colour blindness.

- **The sing line is gold** (`GameTheme.playhead`, was 40 % white). It is the one vertical in the track and the one thing that never moves, so it should not share a colour with the notes going past it or with either singer. Warm against a field that is otherwise cool is what lets the eye find it without hunting.

- **Settings has a Main menu button, in the header rather than under the list.** The header is the part of that screen that does not scroll, which is the whole reason it is there: the hint that used to live at the foot of the list was pushed off the television by a fifth setting, and an exit that can be scrolled off is worse than one that is only on the Back key.

- **The claim screen shows every microphone at once** (`ui/ClaimScreen.kt`). The room is looking at three microphones and the screen was showing one card, so "did it hear *me*?" had to be inferred from a meter that could have belonged to any of them. A card each — drawn microphone, label, one bar — answers it by pointing.
  - **One bar per microphone, and never two at once** (`MicClaim.claimProgress`). Before a claim, a bar says how close *that* microphone is to being claimed: the lower half is getting loud enough, the upper half is holding it, and they join exactly at the middle because leading requires the level to have reached the gate already. The old card stacked a level meter with a hold bar underneath it, which asked the room to read two moving things at once and work out which one meant "keep going".
  - **A claim spotlights its microphone and dims the rest, and the bar changes what it means.** The question has changed from "which one" to "is this one yours", so it becomes a plain live level with no target on it — sing, and the card that moves is the one about to be given your name. That is still the recoverable-by-singing property the previous version was built around; it is just now obvious which card to watch.
  - A microphone already spoken for shows a full, still bar in its owner's colour. It is not measuring anything any more and must not look as if it is.
  - **The microphone glyph is drawn rather than imported.** `androidx.tv:tv-material` ships no icon set and the phone Material icon library would be a dependency for a shape — the same call `LoadingBar` made.
  - **Every card carries a border, and that was found on the television rather than in review.** `trackBackground` is `0xD90E0F16` against a `0xFF0E0E13` ground — invisible, which was fine when one card had a coloured outline and is not fine when there are three. The first screenshot showed text floating in the dark. A 1 dp `noteIdle` line makes a card a card; the spotlit one keeps the singer's colour at 3 dp.

- **Claiming is much harder than it was, because microphones were claiming themselves as they were picked up.** A hand closing round a mic is a loud broadband thump, comfortably over a gate tuned to keep the television out, and it is heard far more by the mic being lifted than by the one on the table — so it passed the dominance test too. Two constants, both in `game/MicClaim.kt`:
  - `CLAIM_LEVEL_HEADROOM` = **1.6**, so claiming needs 1.6× the gate the game will score with. This is the *stronger* form of the old rule that a mic able to claim must be a mic able to score, not a weakening of it.
  - `CLAIM_HOLD_SECONDS` = **0.9**, up from 0.35, and this is the real defence: a thump is over in a fraction of a second, and any dropout restarts the clock. The screen says "Keep singing until one bar fills", because holding a note for the better part of a second is deliberate and not guessable.

- **The drawn keyboard has a cursor** (`ui/TypedQuery.kt`, `ui/KeyGrid.kt`). A system keyboard arrives attached to a text field that has a caret and arrow keys; one drawn on the page has to provide them itself, and without them a single wrong letter at the start of a word costs every letter after it.
  - Left, right, **backspace** (renamed from "del") and **delete** (forward), plus a row of punctuation. Both delete keys are **named rather than drawn**: ⌫ and ⌦ are not reliably in the system font, and a key showing a missing-character box is worse than a key showing a word.
  - `TypedQuery` is a pure type holding the words and the cursor, because two screens drive the same six edits and both have to agree about what pressing left at the start of the text does. Unit-tested, including that a cursor outside the text is refused rather than silently moved.
  - **The grid went from six columns to seven**, which is what paid for all of it. The screen is 540 dp tall and the rail had about twenty dp of slack under the keyboard; seven columns costs two dp a key and buys a whole row back. Keys are 32 dp, down from 38 — which makes the eight rows **shorter** than the seven they replaced, so the layout already measured as fitting is the floor rather than a hope.
  - The caret blinks and **restarts solid on every edit**, so it is never invisible at the moment somebody has just pressed a key and is looking for what happened.

- **Search results are one endless list instead of pages.** The "More results" button was a journey across the screen that had to be made again for every page, and it sat at the end of a grid rather than in the rail with everything else pressable. Scrolling near the end now fetches the next page and appends it.
  - **Each page is ordered as it lands and then never moves.** Re-ordering the whole accumulated list every time a page arrived would reshuffle cards already on screen, which on a television moves the focus out from under a thumb.
  - Guarded on `wanted == loadedPage`: the last-visible index changes many times while a grid settles, and without that guard every one of those frames would ask for another page.
  - Nothing focusable is put at the end of the list. A button there is a place the cursor can be sitting when the ground moves underneath it.

- **A search returns to the top of the results.** A lazy grid keeps its scroll *offset* when its contents change, so searching from halfway down a list left the view halfway down a completely different one — reported as jumping to a random spot, and the same fault the songs grid had. Keyed on a sequence number bumped only when a **first** page lands, because appending must not scroll anywhere.

- **"Music unavailable" is worked out before anybody focuses a card.** It used to wait for focus, which meant the one thing worth knowing before choosing was only ever said about the song already chosen. A paced sweep now walks the results in order, one at a time, stopping a few cards past the last one on screen — so scrolling meets answers that are already there, and nothing is fetched for a page nobody has read.
  - **The verdicts live on `Downloads`**, so searching for the same band twice in an evening does not ask the same question twice. Deliberately **not** written to disk: a video can be taken down or restored between sessions, and a stored "unavailable" would go on refusing a song that had come back — the one error nobody would think to look for.

- **Previews are fetched whole and played from memory** (`audio/playSample`). The song picker's previews never stutter and this screen's sometimes did; the difference is that the picker reads a file off the card while this one streams thirty seconds from Apple over a connection that is *also* fetching thirty covers, checking availability, and quite possibly running a download at fifty megabytes a second. A sample is about half a megabyte, so fetching it in one go moves the whole contest to before playback: the worst a busy connection can now do is start it a moment late.

- **The library's search forgives what people actually type** (`library/FuzzyMatch.kt`). Four rules, each looser than the last: containment; containment with the spaces closed up (so "aha" finds "a-ha" and "gunsnroses" finds "Guns N' Roses"); every word of the query present in any order (so "beatles yesterday" and "yesterday beatles" both find the song); and every word within a typo or two of some word in the text.
  - **Transpositions count as one edit, not two.** Swapping two letters is far and away the commonest mistake on a directional pad, and plain Levenshtein calls "beatels" two edits from "beatles" — so a one-typo budget would refuse the commonest typo there is. Optimal string alignment, capped, with an early exit per row.
  - **An apostrophe is not a word break**, it is a letter that was left out: "don't" normalises to "dont", because that is what gets typed. Every other mark separates.
  - **A query under three letters is never forgiven, only contained.** The old comment was right that a fuzzy match on two letters returns the library; that is now a rule (`FUZZY_MIN_TOKEN`) rather than a reason not to have fuzzy matching at all.
  - **Every word of the query has to answer to something.** One word matching perfectly does not carry a word that matches nothing, which is what stops rule four widening into "any song containing any of these letters".

- **USDB cannot be made fuzzy, and the fix is to ask it a better question.** Its search matches each field as a substring on its own server, so a typo returns nothing and no amount of local cleverness changes that — the only way would be to hold its whole catalogue. What *was* broken and is now fixed is the commonest query of all: **"beatles yesterday" is contained in no artist and in no title**, so the two searches one keyword becomes both returned nothing. A multi-word keyword now also goes out split at the first space, artist and title, which is a real server-side match rather than a guess. Only when neither field was named explicitly, and only for the keyword box — searching is the part of USDB that is not throttled, so the third request is cheap.

**Seven things from the first evening of alpha testing** (2026-09-01, all reported from the sofa and all fixed and re-checked on the television).

- **The library's search was never the problem; USDB's was.** "ymca" and "god gave kiss" both came back empty. The library matcher accepts both — checked against the real chart names before changing anything — so the failures were the download page, where matching happens on USDB's server as a plain substring per field. Two fallbacks now run, and **only when the answer would otherwise be nothing**, because each is another request:
  - **The band's name last.** The keyword is split at the *first* space, which reads "beatles yesterday" correctly and "god gave kiss" backwards. People type the words they remember in the order they remember them, and the band is as often last as first.
  - **An acronym spelled with full stops.** "ymca" can never be a substring of "Y.M.C.A.", so a short single word of letters is also tried as "y.m.c.a" — which is exactly how that whole family is filed. **Verified live: "ymca" now returns Village People.**
  - What cannot be fixed is a *typo* on USDB. Its search is a substring match on their server; forgiving one would mean holding their whole catalogue.

- **A preview kept playing after you walked away from it.** A card reported *taking* the focus and never losing it, so `focused` stayed set: going back to the keyboard left the sample playing, and a new search left it playing for a card that was no longer on the screen. Cards now report both, guarded (focus moves card to card as "lost, then gained", in that order), a new first page clears it, and the player is **stopped rather than paused** — a paused player still holds an audio track open on a device whose output path is a re-encode to E-AC3. The same fix went on the song picker, where walking up to the controls had the same effect.

- **Results are ordered by how well they answer, then alphabetically** (`relevance`). It was one coarse split — every artist match, then everything else — which is right about the big case and blunt about the rest: a song *called* "Queen" ranked below every artist with "queen" somewhere in their name. Six grades now, compared on the same normalised form the library search uses, so "ymca" is as good a match for "Y.M.C.A." as it looks to whoever typed it. Ordering is per page, because pages are appended and never re-sorted.

- **The choppy previews were garbage collection, and the culprit was the availability sweep.** Measured on the television rather than guessed: while previews stuttered, logcat showed **eight collections in four seconds, each freeing forty to sixty-five megabytes of large objects**, and an `ExoPlayerImpl: Init` immediately after "Waiting for a blocking GC". The sweep asks YouTube whether each song's music can be fetched, and a player response runs to megabytes; a check every 1.2 s is a steady stream of multi-megabyte allocations. That also explains the shape of the complaint — it cleared up "if you stay on the page long enough", which is when the sweep runs out of things to ask about.
  - **The sweep now waits while a sample is playing.** Somebody listening to a song is doing the thing the screen is for; knowing in advance whether it can be downloaded is a nicety, and the nicety waits. Re-measured: during playback the large-object churn falls from 40–65 MB a collection to 0–7 MB, and collections spread from eight in four seconds to one every ten or so.

- **A solo arrow is never the singer's own colour.** Purple was correct for the notes, the name and the score and wrong for the arrow, which carries the green→red accuracy scale — so between notes it was purple and on one it was green, which reads as two ideas fighting. It now falls back to the *start* of that scale instead of to the trace colour.

- **Everything stops when the app is minimised** (`ui/PauseWhenBackgrounded.kt`). A preview kept playing after Home, so the launcher sat there with a song coming out of it and nothing on screen to stop it. An `ON_STOP` observer, on both preview players. `ON_STOP` rather than `ON_PAUSE` because a dialog over the app pauses it, and a preview going silent because a permission prompt appeared would be its own small bug. Verified with `dumpsys audio`: an `AudioTrack` in `state:started` before Home, and no player at all after.

- **The song row loops by continuing rather than by jumping.** It used to intercept the two ends and put the row at the other one, which is an answer but reads as a teleport. The list is now the library laid end to end four hundred times over and the row starts in the middle copy, so moving off the last song lands on the first because that is genuinely the next card — nothing is intercepted and nothing moves under you. Verified: from "7 Years" (first by title), one press of left scrolls a single card onto "Ziggy Stardust" (last), with the row reading "…You're Welcome | Ziggy Stardust | 7 Years | 9 To 5…".
  - **A jump picks the nearest copy**, so pressing M while looking at L moves a few cards rather than unwinding two hundred copies back to a canonical first M. Re-filing the library goes back to the middle copy as well as to the first song, because the row's positions are counted in copies of a list that has just changed length.
  - **Below eight songs it does not loop.** About four cards fit across the television, so a shorter library would show a copy beside its own original — the same album twice on one screen, which reads as a bug. A library that short fits on the screen anyway, so wrapping it by jumping is invisible.

**Two adb traps that cost an hour between them**, both worth knowing before driving this keyboard again:

- **`adb shell` inside a `while read` loop eats the loop's input.** It inherits stdin, slurps the rest of the file on its first iteration, and the loop ends after one key — silently, looking exactly like the app ignoring key presses. Redirect it: `adb shell input keyevent "$k" </dev/null`.
- **A key list generated on Windows has CRLF endings, and `input keyevent KEYCODE_DPAD_RIGHT\r` fails silently** — no error, no key. The same `tr -d '\r'` the device paths need, in the other direction.
- Also: sending many key events in one `input keyevent A B C …` call drops some of them. One call per key is slower and is the only reliable way.

**Six things from an afternoon of alpha testing** (2026-09-02, all reported from the sofa).

- **"Repair 7 songs" over a row of chips saying nothing was missing, and every one of the seven failed.** Two faults wearing one symptom, and the second is the one worth keeping.
  - ~~**A song can need a *better* cover, and no filter said so.**~~ **Removed on 2026-09-05, chip and repair together.** Repair covered artwork under `MIN_COVER_PIXELS` — the user's call on 2026-08-24, and still right — but Ready / No music / No video / No artwork all call such a song complete, so the count referred to songs nobody could see. `SongFilterState.SoftArtwork` is now a chip. It is the only filter state the scanner cannot answer on its own, so the set is **passed in** rather than worked out: it falls straight out of the survey the Repair button already runs, which has read and measured every cover, so the filter costs nothing.

Whether better artwork exists anywhere cannot be known without asking iTunes, so the survey *guesses* — and when the answer was no, nothing recorded that, and the same seven songs were counted again on the next look at the card, for ever. The song and a **signature of what was wanted** are now remembered in prefs. The signature carries the cover's own measured size (`RepairPlan.coverPixels`), so a bigger picture arriving by any route makes the attempt worth making again; it deliberately excludes the scan generation, which changes every time the card is read and says nothing about what is wanted.
  - **Applied to the batch only.** A song's own page still offers whatever its plan says: asking again deliberately for one song is a reasonable thing to want, costs a few seconds, and is the only way to overrule this.

- **Coming back from a song landed on the first one.** `rememberLazyGridState` was called *inside* the list branch of the `when`, so opening a song threw the scroll away and returning rebuilt it at the top — on a hundred songs that means finding your place again every time you look at anything. The state is hoisted, the song being inspected is remembered, and coming back scrolls to it and focuses its card. Two steps and both are needed: a lazy grid has not composed an off-screen card, so its focus requester does not exist until the scroll has brought it into view — the same rule the picker documents for its row, and the same wait for frames. The header's own focus effect stands aside while a return is in flight, or the cursor would sit on "Change folder" above a grid scrolled to the middle.

- **"Already yours" on a Godsmack song nobody had downloaded.** The marker was read from **folder names**, which is not the same claim. A folder called `Godsmack - Awake` does refuse a download whatever is inside it — that is deliberate, since two folders for one song is worse than not downloading — but saying the song is *yours* needs the song. It is now matched on artist and title, normalised the way the search normalises them and then closed up, so `Y.M.C.A.` and `YMCA` are one title; and on **equality, never containment**, because "Hello" is inside "Hello Again". A bare folder-name clash still disables the card and says **"Folder name taken"**, which is a fact somebody can act on rather than the app being wrong at them.

- **"tonight tonight" found nothing while "smashing" found the song.** USDB matches a **substring per field** on its own server, and the song is filed as "Tonight, Tonight" — so the phrase is inside no title, inside no artist, and neither half of it is inside "The Smashing Pumpkins" either. All four existing searches were bound to come back empty. The comma is the whole story.
  - The last resort is now to sweep on **one word**, which has no punctuation in it and therefore survives whatever the title does, and to narrow what comes back with the same matcher the song library uses. `longestWord` picks the most selective one — "god gave kiss" sweeps on "gave", not on "god".
  - **A bounded sweep returned as a single page**, not paging. Narrowing a page can empty it, and an empty page stalls an infinite scroll with nothing on screen to scroll — which is the very failure being rescued. Four pages is a hundred and twenty songs deep, and searching is the part of USDB that is not throttled.
  - Title first, artist only if that found nothing, so the ordinary case costs one sweep. Single-word queries are left alone: one word is already a substring, so if USDB has not found it by now it is not there.
  - `SearchPage.narrowed` exists so the screen can say **"Close matches"**: that count means something different from a site total, and reporting one as the other would be wrong in both directions.
  - A song called "Tonight" is a fair close match for "tonight tonight" and is shown; `relevance` puts the exact title first, which is what makes showing it harmless. What is refused is a row answering only half the query — pinned by a test, because that rule is the whole difference between a rescue and a wall of noise.

- **The focused song sits in the middle of the row.** A television has no pointer, so the focused card *is* the cursor, and Compose's default bring-into-view scrolls the least it can — right for a list somebody is dragging, wrong for one somebody is stepping through, because the card lands hard against whichever edge it came in from and stays there. Done with a `BringIntoViewSpec` through `LocalBringIntoViewSpec` rather than by scrolling on focus, and that distinction matters: the spec **is** the scroll the focus already asks for, so there is one movement. An `animateScrollToItem` on top would be a second animation chasing the first. A letter jump lands centred too (`centringOffset`), or arriving at the screen would show a visible slide in from the edge.

- **A "video" that is one photograph now falls back to the visualiser** (Weezer's "Across the Sea", and a good many others). A still image behind a karaoke game is the one background that cannot respond to the music, so it reads as a frozen video rather than as a choice.
  - **The frames it is decided from are the ones already being taken.** The letterbox measurement samples the picture behind a black screen; those same samples now answer "did anything move", so the test costs one comparison per sample and no extra decoding. `measureLetterbox` reads a luma array instead of calling `getPixel` per look, which it wanted anyway — the bar search asks about most pixels several times over.
  - **The test is "any motion at all", not "how much".** A still image decodes to the *same* frame every time, so a photograph held under the audio reads exactly zero changed pixels; the threshold only has to survive dither in the read-back.
  - **It watches for longer than the crop needs (2.4 s) and stops the moment anything moves.** Plenty of real music videos open on a held title card, and calling one of those a photograph would spend the whole song on the visualiser. A moving picture is proved by its second sample, so it pays nothing; only a still image waits out the window.
  - **Decided before anything is revealed**, so there is no switch to watch: the screen goes from the title card straight to the visualiser, exactly as it does for a song with no video file at all.

- **The subtle periodic hitch was the bring-up trace.** Reported as stuttering "at a set interval" in the notes and lyrics — which is what a periodically expensive *frame* looks like: sixty frames cost the same and then one costs more, on a strict two-second beat. The trace sat inside the frame loop and did five `String.format` calls and a log write there. It is its own coroutine now and builds the line on `Dispatchers.Default`; nothing in it is drawn, so nothing in it belongs on the thread that draws. Reading a scorer from another thread is the race the drawing already accepts, and `SongClock` is lock-free by design so that any thread may ask it the time.
  - **Two more periodic costs went with it.** The mic-notice check ran a `filter` sixty times a second to answer a question whose answer is almost always "no"; it asks `any` first. And once a video reached its own end, the sync loop seeked **every 250 ms for the rest of the song** — the video's position stops at the duration while the song's does not, so the drift only grows and every check asked for another decoder flush. Past the end there is nothing left to keep in step with, so it pauses and leaves it alone.

**Why the console games get their arrow to the sing line, measured off their own footage** (2026-09-03). Asked from the sofa: Karaoke Revolution and Rock Band put the pitch arrow right at the line and it does not feel wrong — why did ours have to sit so far left, and would moving it throw a singer's timing?

Two clips were downloaded, measured frame by frame and deleted. Method as ever: find the playhead by looking for the one column that is bright down the whole lane and never moves; get scroll speed by correlating a **fixed-width** slice of the note signature between frames fifteen apart (a sliding-overlap correlation is degenerate — it always prefers the smallest shift); find the arrow by the one colour nothing else on screen has.

| | window across the screen | sing line | arrow offset | in time |
|---|---|---|---|---|
| **Karaoke Revolution** (PS2) | 1.95 s | 14 % of width | 25 px of 1280 | **39 ms** |
| **Rock Band 4** (console, HDMI) | 3.56 s | 22 % of width | ~3 px of 1280 | **~8 ms** |
| **Ours, before** | 2.25 s | 30 % of width | | **113 ms** |

- **Karaoke Revolution does exactly what this app does.** Its arrow is *not* at the line — the tip sits 25 px short of it, which at 2 % of the screen reads as touching. So the design was right; the number was three times too big.
- **Rock Band's cursor really is at the line, and it draws a comet trail of recent pitch streaking off to the left** — occupying precisely the region our `judgedBand` shades. That is how they make an honest offset invisible: not by removing it, but by drawing it.
- **They were not cleverer, they were faster.** A PS2 through composite into a CRT has no HDMI chain, no Dolby re-encode and no picture processing, so the residual was small enough to hide against the line. Rock Band calibrates the whole chain and then does not bother with the last twenty milliseconds.

**Moving our arrow to the line could not throw anybody's timing**, and that is worth stating plainly because it was the reason for asking. The arrow is not a timing cue: timing comes from the notes arriving at the gold line, which is set by the audio and by `displayLeadSeconds`, and none of that changes if the arrow moves. What moving it would cost is *truthfulness* — "the arrow is inside the bar" and "this beat counted" are currently the same statement, and this library's median beat is 54 ms, so at 113 ms the arrow would be drawn over a note two beats ahead of the one it measured.

**So the gap was shrunk instead of hidden: 113 ms → 77 ms**, and 41 of the 36 ms saved were things this app was doing to itself.

| term | was | now | |
|---|---|---|---|
| analysis window centre | 21.3 | 21.3 | physics — `Yin` needs about two periods of 65 Hz |
| **display lead** | **40.0** | **40.0** | the television; now the largest term by far |
| median-of-3 | 21.3 | 10.7 | one hop |
| reading age | 10.7 | 5.3 | half a hop |
| position easing | 20.0 | **0.0** | |

- **The analysis hop is halved, 1024 → 512.** Twice as many readings a second (about 94), which takes a whole hop off the median's delay and half a hop off how stale the newest reading is when a frame picks it up. It costs a second pass of `Yin` per window — the pitch work doubles, from a measured ~45 % of one core for two microphones to ~90 %, on a device with three cores idle. That is the one number here worth re-checking during a real song (`adb logcat | grep -E "Skipped|Davey"`), and if it ever needs to come down the lever is still the one recorded above: decimate before `Yin`, since a voice topping out at 1200 Hz is enormously oversampled at 48 kHz.
- **`DEFAULT_WINDOW_SIZE`, `DEFAULT_HOP_SIZE` and `DEFAULT_SAMPLE_RATE` are named now, and that mattered more than it looks.** Three different latencies are derived from those numbers and two of them are *not* the same quantity: half the **window** is where a reading's centre sits, and the **hop** is how often one is published. Both were written out as `1024.0 / 48_000.0` — correct only by coincidence, since the two happened to be equal — so halving the hop would have silently left two of the three wrong.
- **The position easing is off.** It was the cheaper of the two smoothers to give up: a median discards a wild reading outright where easing only slows one down, so easing was never the thing keeping the arrow steady. The parameter and its tests stay, because the argument for it was real, and a new test pins the *default* at zero — anything non-zero there is a delay and has to be added to `arrowLagSeconds` or the arrow is drawn to the right of the note it earned.

**Live display-lead tuning is back on up and down during a song**, which is the third change and the one that makes the other two checkable. It was here once, it found the original 40 ms, and it was removed when gameplay was cut back to pause and back — with a note saying it was worth restoring if it ever came up again. It has: the display lead is now over half the remaining gap, it is the only term dialled by eye rather than measured, and a menu is the one place it cannot be judged. Five milliseconds a press, written through to the live calibration as well as to the stored setting, with a readout that appears for under two seconds and takes no focus.

**Game mode cannot be triggered *by ALLM* from this device, and it is not for want of an API** (superseded in part by the section below, which finds a route that does work) (measured 2026-09-03). The LG C1 switches itself into Game Optimizer when a source signals HDMI's Auto Low Latency Mode, which is exactly what Android's `preferMinimalPostProcessing` asks for — added in **API 30**, this device's level exactly. `MainActivity` now asks for it. The Shield refuses to carry it:

```
allmSupported false   gameContentTypeSupported false   minimalPostProcessingSupported false
mAllmRequested=false  mGameContentTypeRequested=false  mRequestedMinimalPostProcessing=false
```

The framework drops the request rather than forwarding it, so nothing reaches the television. `deviceProductInfo null` in the same dump says the display HAL is not reporting EDID either — the same shape of gap as the USB audio HAL, and unreachable for the same reason. **The request is kept anyway**: it is three lines, it costs nothing, it logs the answer so the question is not asked again from scratch, and it would start working if the firmware ever gained support. The only way to get game mode on this input today is the LG's own picture-mode control, by hand, which then applies to streaming as well — so the practical answer is to dial the display lead for whichever mode the set normally sits in, which is what the up/down control is for.

**Game mode on the television: three routes, and the one that worked was withdrawn** (2026-09-03; route 3 measured a net loss and turned off on 2026-09-05 — see below). The first answer here was "the Shield cannot signal ALLM, so nothing can be done", and that was true about ALLM and wrong about the question. Pushed on it, and there are three ways in.

**1. ALLM — dead, and not only because of the Shield.** `preferMinimalPostProcessing` is asked for and dropped: `allmSupported false`, `gameContentTypeSupported false`, `minimalPostProcessingSupported false`, and `mRequestedMinimalPostProcessing=false` even after the request. `deviceProductInfo null` in the same dump says the display HAL is not parsing EDID either. **And the Shield is not plugged into the television**: its CEC physical address is `0x2200`, two levels down, through a **Denon AVR-S760H**. So even a Shield that could signal ALLM would need the AVR to pass it, which on that model is the 8K input only.

**2. CEC — closed.** `IHdmiControlService` is running and `mHdmiControlEnabled: true`, but `HdmiControlManager` is a `@SystemApi` behind a signature permission, and `cmd hdmi_control` answers *"No shell command implementation"*. There is no route for an ordinary app, and none for adb either. There is also no standard CEC message for a picture mode; LG's is vendor traffic.

**3. The output mode — this one works, and was then measured during an actual song and turned off** (`ui/LowLatencyVideo.kt`, a setting, now default **off**; the measurement that reversed it is in the 2026-09-05 section below). Everything in this subsection is true of the Shield's own side and is kept for it; what it misses is the ~25 ms the deeper buffer pipeline then costs, which is more than the 8.35 ms it saves.

The insight is that the expensive half of a television's processing is motion interpolation, and **interpolation has nothing to do at 120 Hz** — there is no gap between frames to invent one for — so a set fed 120 Hz skips the slowest thing it does even outside game mode. `preferredDisplayModeId` is settable by an ordinary app, and the Shield offers exactly one mode above 60 Hz: 1920x1080 at 120, because its HDMI is 2.0b and 4K stops at 60.

Measured, same build, the setting toggled between runs:

| | output mode | Shield's own presentation deadline | CPU, 30 focus moves |
|---|---|---|---|
| off | 129 — 3840x2160 @ 59.94 | 17.58 ms | 225 ticks |
| **on** | 121 — 1920x1080 @ 120 | **9.23 ms** | 232 ticks |

- **8.35 ms is banked before the television is involved at all**, and it survived the AVR: `mActiveModeId=121` with the Denon in the path.
- **The picture costs nothing.** Android already composites this whole app at 1920x1080 and upscales on the way out — `mOverrideDisplayInfo` says `real 1920 x 1080` — so all that changes is which box does the upscale, and the C1's scaler is not worse than the Shield's. Nothing on the card is above 1080p either.
- **CPU is +3 % on a menu**, which is nothing. It will not be nothing during a song: gameplay is driven by `withFrameNanos`, so the frame loop and the whole track redraw run 120 times a second instead of 60. That is the reason the setting can be turned off, and the reason to watch `Skipped`/`Davey` during a real song.
- **How much the *television* saves was never measured, and the question is now moot**: what the Shield's own pipeline loses to the mode is larger than anything the set could give back.

**The direct answer is still available and needs one thing from the house: the television is not on the network.** An SSDP sweep found four Shields, two Synology boxes and a Denon, and no LG at all; ports 3000 and 3001 are closed everywhere on the subnet. A networked webOS set takes commands over its SSAP WebSocket — it is what Home Assistant and `bscpylgtv` drive — and a picture-mode change is one of them. That would be the real thing asked for: the app switches the C1 into Game Optimizer as it opens and puts it back as it closes, automatically, after a single pairing prompt accepted once on the television. It is not built, because it cannot be tested against a television that is not there, and the exact settings endpoint on webOS 6 is the part worth verifying rather than assuming.

**Six more from testing, and the 120 Hz trick turned out to be a net loss** (2026-09-05). All six driven and measured on the real television.

A song with no artwork that iTunes has none for would otherwise be counted into "Repair N songs" for ever.

**And the interesting one: driving the television at 120 Hz makes it *worse*, and the report that found it was "the music video looks choppy".**

Measured on the television, same build, same song, 50 s of Thriller, the setting the only difference:

| | frames | janky | frame p50 | GPU p50 |
|---|---|---|---|---|
| off (2160p60) | 2882 | **2 (0.07 %)** | **5 ms** | **2 ms** |
| on (1080p120) | 2877 | 2866 (99.6 %) | 31 ms | 16 ms |

The same again on a song with no video, so it is the mode rather than anything about decoding a picture: 2908 frames, 99.6 % janky, GPU 15 ms.

- **It is not dropped frames, and `gfxinfo` alone would have said it was.** `framestats` settles it: at 120 Hz the app is asked for a frame every **16.67 ms**, 119 times out of 119, and delivers every one. Android runs the app at 60 fps and shows each frame for two refreshes; the cadence is perfectly regular. The jank percentage is an artefact of gfxinfo measuring against the display's 8.33 ms period. **Read `framestats` before believing a jank number** — it is the only thing that distinguishes "late" from "paced".
- **What is real is a pipeline two frames deeper.** A frame finishes 31 ms after the vsync it was drawn for against 5 ms with the mode off, and the wait sits between queueing one frame and starting the next — buffer back-pressure. So the mode **costs about 25 ms of display latency to save the 8.35 ms of presentation deadline it was adopted for**, which inverts its entire justification.
- **It also explains why the complaint was about the video specifically.** The notes are drawn on the app's own steady 60 fps and look the same either way. The video is not: ExoPlayer snaps each decoded frame to a display vsync — an 8.33 ms grid at 120 Hz — while the app samples the texture on its own 16.67 ms one, so a 24 fps video lands on a wandering 2-or-3-frame cadence instead of a steady one.
- **So the setting defaults off.** Kept rather than deleted, because the measurement is about this chain — Shield through a Denon AVR into a C1 — and the dozen lines that make it repeatable are worth more than they cost. Nothing else in the app reads it.

**And the CPU was never the problem.** Measured during a song with video, both microphones capturing, from `/proc/<pid>/stat`: **44 % of one core**, with 276 % of the four idle. The ~90 % figure in the 2026-09-03 notes was a projection for the *pitch work alone* after the analysis hop was halved, and it is not what the whole app costs.

**A chart that is out of sync is almost never the app, and there is now a way to prove which.** "Magic Dance" was reported as wildly out of time with its audio and video (2026-08-18). Every chart on the card is `#VERSION:1.0.0` and the rest play fine, so the format was not it. The method that settled it:

- **Correlate the chart's *melody* against a chroma profile of the mp3**, sweeping the offset. Score each analysis frame the chart says is being sung by how much of that frame's energy sits in the pitch class it asks for, and find the offset that maximises it.
- **Rhythm is useless for this and pitch is not.** The first attempt correlated note onsets against an energy envelope and failed its own control: a 4/4 pop song scores nearly the same at every bar line, so it "found" a +34 s offset for a song that is perfectly in sync. The sequence of pitch classes a song moves through is close to unique; the sequence of onsets is not.
- **Always run two known-good songs as controls first.** They peak within 0.09 s of zero at 1.5–1.9× the mean; a wrong transposition of the same song scores 1.17–1.25×. That band is what makes a verdict possible, and without it the numbers mean nothing.

Magic Dance scores **1.09× at every offset, every transposition and every tempo**, and windowed alignment scatters (+21.7, −18.0, +13.4, −11.5, +15.1 s) where a good song locks to −0.14…−0.05 s in every window. Its `.txt` and its `.mp3` are simply different recordings — not a `#GAP` error, so **no offset can fix it**; the chart or the audio has to be replaced. Its pitches are internally consistent (repeated lines repeat their melody to ±1 semitone, the signature of an auto-generated chart), and the mp3 carries `Audio Source=z6DJmp21vcQ`, so the pack's chart and its media were plausibly sourced independently.

**Sweeping all 71 folders is what makes that a finding rather than an anecdote**: 49 scoreable, **48 aligned at ~0 s, and Magic Dance the only mismatch in the library**. The other 22 folders hold a `.txt`, covers and sometimes an `.mp4` but **no audio file at all**, which is exactly why the library shows 49 — the sweep's failure set and the app's agree song for song. **The video fallback idea is dead**: those `.mp4`s were checked and carry a single `h264` stream with no audio, and several folders have no media beyond the artwork. They are incomplete downloads, not misfiled ones.

- **The document picker is awkward with a remote, not broken — and the difference is one rule.** The claim history here is worth keeping because it was wrong twice. First it was called fully navigable, on the strength of driving it over adb, which can *tap* and so proved the wrong thing. Then it was called unreachable, which was too strong. What is actually true, measured on the device on 2026-08-19: **"USE THIS FOLDER" holds focus every time a folder opens, and cannot be reached again once focus leaves it.**
  - **The mechanism is content overflow.** `dir_list` (a `RecyclerView`) has bounds `[0,0][1920,1080]` — the entire screen — with the confirm button at `[28,984][1892,1080]` overlaid on top and **no bottom padding reserved for it**. When the content is taller than the viewport the last row's bounds run to y=1080, so the button is not *below* anything: Android's focus search for `FOCUS_DOWN` looks for a focusable whose bounds start below the current one, finds none, and gives up. Six items in grid mode are ~470 px tall each, so two rows already overflow — a folder of songs always will.
  - **But the picker focuses the button itself on arrival**, which is what makes it usable anyway. Verified by key events inside the 71-song folder — the hardest case there is — `FOCUS text=[USE THIS FOLDER] id=android:id/button1`. Press it there and then, and the whole grant is a walk down the tree and one press. Move up into the grid first and you are stranded: after eleven DOWNs the dump reports no focused node at all, and the only way back is Back, which leaves the folder and re-enters it with the button focused again.
  - That rule is small enough to say in two sentences, which is why `ui/PickerHint.kt` says it on both screens that open the picker rather than the app working around it.
  - **Asking for a whole drive was the workaround, and it was reverted on 2026-08-19 after a day.** `StorageVolume.createOpenDocumentTreeIntent()` opens the picker at a volume root, which is the one place the grid cannot overflow, and `StorageManager.storageVolumes` enumerates drives with no permission at all — so it worked, and it is in git if it is ever wanted. It was the wrong trade: a drive is not somewhere anybody *keeps* songs, so it left the user unable to say where songs are or where a download should go, in exchange for removing a hint that turned out to be two sentences long. **A workaround that costs the user the ability to express what they meant is more expensive than the bug.**
  - The *confirmation dialog* that follows is fine — D-pad reaches CANCEL and ALLOW normally. Only the button before it has the rule.
  - If a grant is ever needed without a remote to hand: `adb shell input tap 960 1032` presses it (bounds are already in 1920x1080 input space), then tap ALLOW.
- **`MANAGE_EXTERNAL_STORAGE` reaches the card completely — but cannot be granted on this device** (both measured 2026-08-18 with a temporary probe in `MainActivity`).

So a public `sdcardfs` volume is **not** an obstacle, which was the open question.
  - **Ungranted, an app can already read the card** — `canRead=true`, 71 children — but writes fail `EPERM`. Reading was never the thing SAF was buying.
  - **There is no UI to grant it.** `android.settings.MANAGE_ALL_FILES_ACCESS_PERMISSION` resolves to *no activity at all* (`cmd package query-activities` → "No activities found"): the Shield ships `com.android.tv.settings`, and the phone Settings page that hosts the All-files-access toggle is not in it. adb is the only route.

**The whole chain is verified end to end on hardware.** Playing the calibration song with a mic at the speaker, the first pass scores **9766–9922 / 10000 (125–127 of 128 beats)** using the shipped 127 ms default. The "singer" is the song itself, so a correct system has to score near the maximum — that number is the proof that playback, capture, pitch detection, timing and scoring all agree.

**Measured latency: 127 ms round trip**, from four runs whose medians landed within 3 ms (124–132). This is now `SyncCalibration.DEFAULT_LATENCY_SECONDS`: a measured default, not a guess, because the app targets exactly one device and one TV.

Findings worth keeping:
- **Most of the 127 ms is Dolby.** The Shield re-encodes to E-AC3 for HDMI (`AudioOut_3D5`, type DIRECT) and the TV decodes it again. Switching the Shield's audio output away from Dolby would cut most of it — re-run the calibration if that or the TV ever changes.
- **The split matters for what is drawn.** Scoring subtracts the whole 127 ms; lyrics and the pitch bar must subtract only the *output* share (~106 ms), because that is how far behind the player the singer's ears are. Rendering at the raw player position would push singers early and then score them for it. See `heardSongTimeFor` vs `songTimeFor`.
- **The first note after playback starts is ~65 ms late**, every time (samples like `[192, 134, 121, 122, 130, …]`). The audio pipeline is still re-syncing. A median absorbs it, which is why the probe uses one — but expect the very first note of a real song to be judged slightly late.
- Residual onset jitter is about ±15 ms, roughly one analysis hop plus room acoustics.
- **Frame-driven loops stall when the display sleeps.** `withFrameNanos` simply stops resuming, so playback ran on with nothing advancing the game — this looked exactly like a hang. `MainActivity` now sets `FLAG_KEEP_SCREEN_ON`, which gameplay needs regardless.

`PlayerScorer` is not thread-safe and capture runs on its own thread. Timestamp each reading where it is produced, then drive `update()` and read `snapshot()` from one thread — or take a lock, as `SyncCalibrationScreen` does, since its per-pass teardown races the capture threads.

Deliberately not done in the pitch layer: no smoothing/median filter over readings. Raw YIN proved stable enough on the real mics that adding one would only hide information. Revisit only if scoring shows dropouts.

Deliberately not done in scoring: no seeking. The scorer walks its notes with a forward-only cursor, so a practice mode that jumps around a song needs `reset()` and a rebuild, not a rewind.
